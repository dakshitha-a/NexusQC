# Create with: conda create -n qc-agent python=3.11 && conda activate qc-agent
# Then: pip install -r requirements.txt
#
# EVERY version here is pinned, and R-059 is why. Thirty-three of thirty-five
# lines carried no specifier at all, including langgraph, langchain and the
# whole langchain-* family, which sit directly under the agent loop and make
# breaking changes across minor releases. The Dockerfile runs a plain
# `pip install -r requirements.txt` with no constraints file, so the image was
# whatever PyPI served on the day it was built, and two installs a month apart
# were two different applications. The file already argued for pinning where
# it mattered ("The point of the pin is that a fresh install works first
# time"), and check_destructive.sh already flagged a newly added unpinned
# package as a hazard; the argument simply had not been applied to the rest.
#
# The versions below are what the working deployment actually ran, taken with
# `pip freeze` inside the running api container rather than resolved fresh, so
# this pins a combination that is known to work rather than one that merely
# solves.
#
# Bump a pin deliberately, when you want the capability, and rebuild to check
# it. Do not bump them as routine maintenance.

# PINNED, and pinned together with pyscf-forge below. The two are a compiled
# pair: pyscf-forge has no wheel for this version, so pip builds it from
# source against whatever pyscf is present, and it declares its dependency as
# a bare `pyscf` with no version bound at all. Left to float, a later pyscf
# could satisfy that bound and still not be what pyscf-forge was compiled
# against. This is the version every capability row for the multireference
# methods was verified on.
#
# Bump both deliberately, as part of adding support for whatever the newer
# version makes possible, and re-run scripts/spikes/spike_pyscf_caps.py --
# never as routine maintenance. The point of the pin is that a fresh install
# works first time.
pyscf==2.14.0
# Pinned like everything else since R-059, but for a different reason from
# the pair above and worth keeping the distinction. Unlike pyscf-forge this
# ships prebuilt wheels, so it cannot fail to BUILD, and it binds to the
# standalone dftd3/dftd4 libraries rather than compiling against pyscf's
# internals -- so it was left floating deliberately while those two were
# pinned to each other. What changed is the argument for pinning: not "this
# combination compiles" but "two installs a month apart are the same
# deployment".
#
# Dispersion corrections for PySCF's DFT. libxc itself needs no entry here --
# it ships inside the pyscf wheel, which is why bare `wb97x` and `wb97x-v`
# already run. What is genuinely absent without this package is the D3/D4
# family: `pyscf.scf.dispersion` imports `pyscf.dispersion` in a try/except
# and every dispersion-corrected functional then fails at run time with
# "dftd3 not available. Install them with `pip install pyscf-dispersion`" --
# b3lyp-d3bj, wb97x-d3bj, wb97m-d3bj and the -d4 variants alike.
#
# Note this does NOT enable `wb97x-d3` or `wb97x-d` on PySCF. Those two are
# on a hard-coded `_black_list` in pyscf/scf/dispersion.py and raise
# NotImplementedError regardless of what is installed; ORCA is the engine
# for those (see docs/PARSER_GAPS.md). `wb97x-d3bj` is PySCF's supported
# near-equivalent.
pyscf-dispersion==1.5.0
# MC-PDFT and L-PDFT (pyscf.mcpdft). These live in pyscf-forge rather than
# the core pyscf wheel, and they are NOT optional the way block2 is: the
# capability rows in app/chemistry/registry2/capabilities.py claim mcpdft
# and lpdft unconditionally on verified runs, so without this package those
# two methods fail at dispatch rather than being quietly withdrawn from the
# menu. Note the distribution is named `pyscf-forge` but the import path is
# `pyscf.mcpdft` (a namespace package), so `import pyscf_forge` raising
# ModuleNotFoundError is not evidence of a broken install.
#
# NEVPT2 needs nothing here: pyscf.mrpt ships in the core wheel.
#
# **This one compiles at install time, and needs a BLAS to do it.** PyPI has
# wheels for 1.0.x only; 1.1.1 is an sdist, so pip runs its CMake build, which
# does `find_package(BLAS)`. The Dockerfile installs libopenblas-dev for
# exactly this, so the supported install path (scripts/install.sh, which
# builds the image) needs nothing from you. Installing this file directly
# into a bare virtualenv is a different matter: on a machine with no BLAS
# development headers the build dies several minutes in on
#
#     CMake Error ... Could NOT find BLAS (missing: BLAS_LIBRARIES)
#
# which is an opaque way to be told to `apt install libopenblas-dev` (or the
# equivalent). Recorded here because the bare-metal developer setup in
# CLAUDE.md bypasses the image entirely and so gets no help from it.
#
# Pinned for the same reason as pyscf above, and to the version it is
# compiled against.
