# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A conversational computational-chemistry agent (WebMO-style): a React single-page app talking to a FastAPI backend that wraps a LangGraph tool-calling agent, backed by a local LLM served via Ollama's OpenAI-compatible endpoint. It resolves molecules by name/SMILES, elicits missing job parameters instead of guessing them, runs quantum chemistry jobs as background subprocesses across PySCF/ORCA/BAGEL, and answers follow-up questions from a RAG knowledge base of uploaded manuals/papers. A prior Streamlit UI (`app/main.py`, `app/ui/`) was fully retired and deleted once the React frontend reached parity — comments/notes below that reference "the still-running Streamlit UI" or `app/main.py` as a live fallback describe that now-removed transitional state; treat them as historical context on *why* a given design choice exists, not as a description of code that's still there.

## Running it

Two processes: the FastAPI backend and the Vite dev server for the frontend.

```bash
# Terminal 1 -- backend (binds to localhost only; single-user, local-only app)
source /home/qcuser/apps/miniconda3/etc/profile.d/conda.sh && conda activate qc-agent
cd /data/qcuser/9.LLM_for_CASSCF && PYTHONPATH=$PWD python3 -m server.main

# Terminal 2 -- frontend (system Node is too old for Vite; use a dedicated env)
conda activate node20   # conda create -n node20 -c conda-forge nodejs=20
cd /data/qcuser/9.LLM_for_CASSCF/frontend && npm run dev
```

Open the URL Vite prints (default `http://localhost:5173`); its dev server proxies `/api/*` to the backend on port 8000, so no CORS setup is needed for local use.

The `qc-agent` conda env (Python 3.11) has everything in `requirements.txt` installed. There is no test suite; the way to validate a *backend* change is to invoke the relevant runner function directly, e.g.:

```bash
PYTHONPATH=$PWD python3 -c "
from app.chemistry.molecule import resolve_molecule
from app.chemistry.jobs.base import JobSpec, get_job_manager
m = resolve_molecule('water')
spec = JobSpec(method='single_point', engine='pyscf', molecule=m.to_dict(), params={'method':'hf','basis':'sto-3g'})
print(get_job_manager().submit(spec))
"
```
or drive the LangGraph agent directly with `app.agent.graph.invoke_turn({"messages": [...]}, config)` to test a full conversational turn without the UI, or curl the FastAPI routes directly (`server/routes/`) once `python3 -m server.main` is running.

For *frontend* changes, launch both dev servers headless and drive the app with Playwright (`chromium` browser only — `playwright install chromium`, no `--with-deps`, no sudo available) rather than trusting a code read — several real bugs here only showed up under real browser interaction, not code inspection: React 18 Strict Mode's dev-mode double-invoke of effects (mount→cleanup→remount) nulls a ref *before* running its cleanup function, so a "clear the container in cleanup" fix for a leaking 3Dmol WebGL context was silently a no-op; the actual fix clears the container at the *start* of the init effect instead (see `frontend/src/molecule/MoleculeViewer.tsx`). Also: `page.screenshot()`/`locator.screenshot()` cannot reliably capture WebGL canvas content — use `canvas.toDataURL()` via `page.evaluate()` instead when verifying anything rendered by the molecule/MO-cube viewers.

## Architecture

**Job execution is fully decoupled from the agent/UI.** `app/chemistry/jobs/base.py`'s `JobManager` submits a `JobSpec` and immediately returns a `job_id`; the actual work runs in a subprocess (`python -m app.chemistry.jobs.{pyscf,orca,bagel}_worker <spec.json>`) so a crash or long-running calculation can never block the FastAPI server process or the agent's tool-calling loop. Status/results are written to `data/jobs/<job_id>/{status,result}.json` via atomic temp-file-then-rename writes (`_atomic_write_text`) — plain `write_text` truncates before writing, which races with the frontend's polling reads (`server/routes/jobs.py`, lock-free — see its module docstring for why this must never go through `read_state()`/`_graph_lock`). The `app.chemistry.jobs.registry` module is the single source of truth for which engine handles which method (`DEFAULT_ENGINE`/`ALLOWED_ENGINES`) and which params are required per job type (`REQUIRED_PARAMS`) — the agent's `submit_job` tool consults this to decide what to ask the user for, rather than hardcoding elicitation logic per method.

**Each engine's runner + worker pair follows the same shape**: `{engine}_runner.py` has pure functions `run_<method>(molecule, params) -> {"summary": ..., "artifacts": ...}`, and `{engine}_worker.py` is the subprocess entrypoint that dispatches by method name and writes the `JobResult`. PySCF results come straight from PySCF's own Python objects. ORCA/BAGEL have no structured output, so `orca_runner.py`/`bagel_runner.py` regex-parse plain-text output — those patterns were derived from actual runs on this machine's ORCA 6.1.1 / BAGEL 1.2.2 installs, not from documentation alone, because exact stdout formatting isn't guaranteed across versions. `N_CORES` in `config.py` is deliberately computed by shelling out to `nproc`, not `os.cpu_count()`/`os.sched_getaffinity()` — both of the latter report the host's full raw logical CPU count (255), which silently made ORCA request far more MPI ranks than sensible. On this specific host that smaller number isn't actually a cgroup CPU quota, despite an earlier version of this note (and `_detect_usable_cores()`'s own docstring, before it was corrected) claiming so — there is no cgroup CPU limit here at all (`cpu.max` is unlimited at every level of the session's cgroup hierarchy, confirmed by reading it directly, and `os.sched_getaffinity(0)` returns all 255 host core IDs, i.e. nothing pins this process to a subset). `nproc` is actually picking up the `OMP_NUM_THREADS=8` environment variable set in this host's shell profile — GNU `nproc` prioritizes that env var when present — meaning `N_CORES=8` is a voluntary courtesy convention for this shared host, not a kernel-enforced ceiling. See the resource-headroom architecture note below for what this implies for the job-admission gate.

**LangGraph state (`app/agent/state.py`) needs `NotRequired` + custom reducers, not just `Optional`.** `AgentState.molecule` and `.active_job_ids` are side-channel fields tools mutate via `Command(update=...)`, separate from the `messages` ReAct loop. Two non-obvious requirements: (1) they must be `NotRequired[...]`, not just `Optional[...]` — on a brand-new thread the keys are genuinely absent, and `ToolNode` validates injected `state` against a pydantic model derived from this TypedDict *before* any tool body runs, so plain `Optional` still fails validation on every tool call in a fresh conversation; (2) they need custom reducers (`_last_molecule`, `_append_job_ids`) because a single LLM turn can emit multiple tool calls in one batch (e.g. `set_molecule` + `submit_job`, or two `submit_job` calls) that all read the same pre-batch state — without a reducer, LangGraph's default channel either silently overwrites one write with another or hard-errors on multiple writes in one step. `generate_job_input` accepts an optional `molecule_identifier` so it can resolve the molecule itself when the user names one in the same message as the job request, instead of depending on a same-batch `set_molecule` call whose effect it can't see yet; `submit_job` deliberately does *not* accept it (see below).

**`submit_job` gates actual execution behind a real LangGraph `interrupt()`, not just prompt instructions.** After building the `JobSpec` and rendering its input preview (`app/chemistry/jobs/preview.py`, dispatching to each engine's `build_input_text`/`build_input_preview`), it calls `interrupt({...})`, which pauses the graph and raises `GraphInterrupt`; `graph.invoke()` returns with the state plus a `__interrupt__` key instead of completing, and the paused task's payload is also readable later via `graph.get_state(config).interrupts` (wrapped as `pending_approval()` in `graph.py` so a page reload while approval is pending still shows the card). The UI resumes with `resume_turn(Command(resume=...))`. This means the safety property — no job runs without a human clicking Approve — holds even if the LLM never asks for confirmation itself, since the pause is structural, not prompt-dependent. The one sharp edge: per LangGraph's docs, *"the graph resumes from the start of the node, re-executing all logic"* — everything in `submit_job` before the `interrupt()` call reruns on resume and is discarded, including a fresh `JobSpec` with a **new random `job_id`** (`JobSpec.job_id`'s `default_factory` reruns too). Two consequences drove the actual design: (1) `submit_job` never resolves `molecule_identifier` itself (unlike `generate_job_input`) — a network-backed name lookup redone on every resume could return a different molecule than the one the user actually approved, or raise on a transient failure and crash the approval click outright (verified empirically: an exception in the pre-interrupt code path during resume propagates straight out of `resume_turn`, it is *not* caught into a ToolMessage the way a normal tool exception is); the molecule must already be committed to state via an earlier/separate `set_molecule` call. (2) The interrupt payload includes `spec.to_dict()`, and the UI round-trips that *exact* dict back through `Command(resume={"approved": True, "spec": ...})` — the actually-submitted job uses `JobSpec(**decision["spec"])`, not a locally-rebuilt spec, so the job that runs is always bit-for-bit what was shown and approved, regardless of what the discarded re-execution produces. `generate_job_input` (preview-only, no `interrupt()`, no re-execution) has none of these constraints and freely resolves `molecule_identifier` inline.

**The approval card lets the user hand-edit ORCA/BAGEL input text before running it, but not PySCF's.** ORCA (`.inp`) and BAGEL (JSON) are genuine text formats the engine binary parses itself, so editing them changes nothing about the trust model — the binary was always going to interpret whatever text it's given. PySCF has no such file: its "preview" (`pyscf_runner.build_input_preview`) is a synthetic driver script standing in for direct API calls, so there's nothing for an edit to actually change at execution time; the approval card renders it as read-only `st.code` instead of `st.text_area` (`_EDITABLE_ENGINES = {"orca", "bagel"}` in `components.py`). When the user edits the text, `render_approval_panel` validates it (`app/chemistry/jobs/validate.py` — structural/keyword sanity checks, not a full grammar: balanced ORCA `%...end` blocks including single-line self-closing ones like `%pal nprocs 8 end`, a recognized geometry block, valid element symbols; JSON validity + required blocks for BAGEL) **before ever calling `resume_turn`** — a typo gets caught and displayed in place with no LLM round-trip, and the interrupt stays pending so the user can fix it and click "Run edited" again. `submit_job` re-validates server-side too (defense in depth, not the primary gate) before writing the text into `spec.params["_raw_input"]`; `orca_runner`/`bagel_runner`'s `run_*` functions check for `_raw_input` first and use it verbatim (byte-identical to what was shown, not re-serialized) instead of regenerating from structured params, falling back to the old codepath when it's absent so a direct `JobSpec` submission (e.g. the testing snippet above) still works unchanged. Because an edit can change what the engine actually prints (a different method keyword, a different BAGEL `nstate`), the job-type-specific output parser may not find what it expects after a real run — both runners wrap summary-building in a `_safe_parse` helper that turns that into a clear "ran fine but couldn't parse X, raw output at \<path\>" error rather than a bare traceback or (worse) silently wrong numbers; this is a deliberate "best-effort" choice over trying to re-derive parser expectations from the edited text.

**Atom numbering is 1-based everywhere a user or the LLM references an atom** — the labels drawn in the React molecule viewer (`frontend/src/molecule/MoleculeViewer.tsx`, via 3Dmol's `addLabel`), the Z-matrix panel (`app/chemistry/zmatrix.py`), `orbital_indices`, and `coordinate.atoms` for `pes_scan` all agree on this, so a number a user reads off the 3D view is directly usable in a scan spec. RDKit's `rdMolTransforms` (used internally by `_internal_coordinate_scan` in `pyscf_runner.py`) is 0-based, so that function subtracts 1 right at its boundary rather than leaking the RDKit convention outward. `zmatrix.py`'s Cartesian→Z-matrix conversion picks reference atoms by nearest-previously-placed distance (not real bonding) and is validated by an independent NeRF-based Cartesian reconstruction (round-tripped to <1e-14 Å pairwise-distance error on water/CO₂/benzene/acetylene in ad hoc testing) — colinear reference triples (unavoidable somewhere in any strictly linear molecule) report a `0.0` sentinel dihedral rather than raising, since the dihedral is genuinely undefined there.

**Excited-state methods (CIS, TD-HF/RPA, TDA-DFT, TDDFT, EOM-CCSD, state-averaged CASSCF, CASPT2) route through existing job_types rather than one-job-type-per-method.** `tddft`'s `qc_method` ('hf' vs 'dft') combined with `use_tda` covers CIS/TD-HF/TDA-DFT/TDDFT — `tdscf.TDA`/`TDDFT` are dispatchers that pick their concrete implementation from the reference wavefunction's type, and an HF reference has no XC kernel, so TDA-on-HF *is* CIS; ORCA's `%tddft` module does the same auto-selection based on whether the keyword line is a functional or plain `HF` (confirmed: energies and oscillator strengths from a real ORCA CIS run agree with PySCF's `tdscf.TDA(scf.RHF(...))` to 5 decimal places). `eom_ccsd` is its own job_type (always post-HF-CCSD, no method choice) added specifically because PySCF's `EOMEESinglet` has no oscillator-strength/transition-dipole support at all (confirmed by inspecting the class — no such method, unlike `tdscf`'s built-in `oscillator_strength()`), while ORCA's `orca_mdci` module computes them by default; `DEFAULT_ENGINE["eom_ccsd"] = "orca"` for that reason, with PySCF available (energies only, explicit `oscillator_strengths_note` in the summary) if explicitly requested. CASSCF has the same asymmetry — none of PySCF/BAGEL's CASSCF paths compute oscillator strengths in this app, but ORCA's `%casscf` block does when given `DoDipoleLength true`, so `casscf` gained `orca` as a *non-default* allowed engine, and `default_engine()` takes an optional `params` argument so a caller passing `want_oscillator_strengths=True` gets mechanically routed to ORCA regardless of engine default — deliberately *not* left to the LLM to infer from phrasing, since this codebase has already hit one incident (see the `NotRequired` note above) where prompt-dependent behavior was misdiagnosed for hours instead of being a mechanical, testable rule. CASPT2 stays BAGEL-only and energies-only (ORCA doesn't implement CASPT2 — it has NEVPT2 instead) since no engine available here computes CASPT2 transition dipoles either. All of the above ORCA output formats (EOM-CCSD's `EOM-CCSD RESULTS (RHS)` energy block plus its `SPECTRUM FOR LEFT-RIGHT TRANSITION MOMENTS` oscillator strengths — the balanced choice among the three transition-moment tables ORCA prints by default, since the CC Hamiltonian is non-Hermitian and right-only/left-only are each one-sided; and CASSCF's post-convergence `CAS-SCF STATES FOR BLOCK` table, bounded to exclude the near-identical pre-convergence `INITIAL CI STATE CHECK` block that has the same `ROOT N: E=...` line shape) were derived from real ORCA 6.1.1 runs on this machine, not the manual alone, following the same practice as the original single-point/frequency/TDDFT regexes.

**The agent can write and register its own tools at runtime (`create_tool` in `tools.py`, `app/agent/dynamic_tools.py`), gated by the same `interrupt()`-based human approval as `submit_job`, not by prompt instructions.** Every dynamic tool is constrained to one fixed shape — a single Python module defining exactly `def run(params: dict) -> dict:` — deliberately, so the rest of the system never needs to safely introspect or execute untrusted code just to build a calling schema: `_make_tool()` in `dynamic_tools.py` wraps every persisted tool in an identical `StructuredTool` (verified that `InjectedState`/`InjectedToolCallId`/`Command` returns work through `StructuredTool.from_function` exactly like the `@tool` decorator, via a direct test) whose body shells out to `dynamic_tool_worker.py`, a subprocess entrypoint in the same shape as the QC job workers — crash containment, not a security sandbox (documented as such in `dynamic_tools.py`'s module docstring); the actual safety gate is `validate_tool_code()`'s AST-based import allowlist/banned-call blocklist (`eval`/`exec`/`compile`/`__import__`/`globals`/`locals`, no `subprocess`/`socket`/`shutil`/network) plus the mandatory human review step. Tools persist to `data/dynamic_tools/<name>.{py,json}` (gitignored, like the rest of `data/`) and `load_dynamic_tools()` re-scans that directory on every call rather than caching, so a tool approved in one session is available in any other without a restart. Because the compiled graph's `ToolNode` is built once from a fixed tool list at `build_graph()` time, a newly-approved tool needs the graph rebuilt to become callable (`invalidate_graph_cache()` resets `_compiled_graph` to `None`; the next `get_graph()` call rebuilds it from `get_all_tools()`'s current contents against the *same* persistent sqlite connection via `_get_checkpointer()`, not a fresh one, so rebuilding doesn't leak a connection or lose checkpointed state — verified that a second `SqliteSaver` wrapping the same connection sees state written through the first). **`invalidate_graph_cache()` must never be called from inside a tool function.** This was a real deadlock, not a hypothetical: `ToolNode` runs tool calls on its own `ThreadPoolExecutor` worker thread (confirmed empirically), not the thread that called `.invoke()` — so a tool that acquires `_graph_lock` blocks forever, since the calling thread is holding that same lock for the entire `.invoke()` call while it waits for the worker thread to finish, and the worker thread is waiting to acquire the lock the calling thread already holds. Switching `_graph_lock` to an `RLock` does *not* fix this (reentrancy only helps a lock's *own* thread reacquire it; these are two different threads) — `create_tool` only ever persists the tool to disk; `server/routes/tools.py`'s tool-approval endpoint calls `invalidate_graph_cache()` itself, from the request-handling thread, strictly after `resume_turn()` has already returned and released the lock.

**The React frontend separates polling from expensive rendering.** Job status/list is polled via TanStack Query (`frontend/src/lib/queries.ts`, `useJobQuery`/jobs-list hooks) hitting `server/routes/jobs.py`'s lock-free disk reads (`read_spec`/`read_status`/`read_result` — never `read_state()`/`_graph_lock`, so a polling tab is never stalled behind an in-flight chat turn anywhere in the process; see that module's docstring). The MO-cube viewer (`frontend/src/jobs/MoCubeViewer.tsx`) and other job-artifact viewers are mounted only when `JobDetailDrawer.tsx` opens for that specific job — React's own mount/unmount lifecycle achieves what a Streamlit `st.fragment` split had to do by hand: they're never rebuilt by an unrelated re-render or polling tick, so an in-progress WebGL rotation/zoom is never discarded from under the user. The live "tail -f"-style job log (`frontend/src/jobs/LiveLogPanel.tsx`, `GET /api/jobs/{id}/log`) *is* deliberately on its own 1.5s TanStack Query `refetchInterval` gated on `status === "running"` — a raw log tail is cheap, low-stakes state, not worth a second SSE event type.

**A chat turn from the composer is submitted via `POST /api/threads/{id}/messages`, which returns `202` immediately and runs the turn on its own background thread** (`_run_turn` in `server/routes/chat.py`), streaming progress to the browser over `GET /api/threads/{id}/events` (SSE, `server/sse.py`'s `SSEHub`/`event_stream`) rather than blocking the HTTP response — the same reason `stream_turn`/`stream_mode` exists over a blocking `invoke()` at all, just pushed one level further from a blocking Streamlit script to a blocking HTTP request. `_run_turn` requests `stream_mode=["updates", "messages"]` (`stream_turn_tokens` in `graph.py`) so real per-token text deltas (`"messages"` mode, confirmed empirically to arrive as genuine incremental chunks through Ollama's OpenAI-compatible endpoint, not one buffered blob) and tool-call progress (`"updates"` mode) come out of the same stream, published as `token`/`agent_step`/`message`/`interrupt`/`turn_complete`/`error` SSE events. The frontend renders the user's own message immediately (`optimisticUserMessage` in `frontend/src/lib/chatStore.ts`, before the POST even completes) and appends `token` deltas to an in-progress assistant bubble by `message_id`, then reconciles with the authoritative final `AIMessage` once the `message` event for it arrives — the same "don't wait for the whole turn to draw anything" fix the old Streamlit UI needed, achieved through real streaming instead of an `st.status` container. `_run_turn` holds `_graph_lock` for its entire iteration, same as `invoke_turn`/the old `stream_turn` — not a new contention source. `resume_turn` (job/tool approval, `POST /api/threads/{id}/approvals/{job,tool}`) is deliberately left non-streaming (a single blocking call): those are one-click resumes with no user-authored message to render early, so `_publish_new_messages` in `chat.py` just diffs message ids before/after the call and publishes whatever's new once it returns.

**The UV/Vis plot tool (`plot_excited_state_spectrum` in `tools.py`) writes its PNG as a job artifact after the job already completed**, not as part of the original `JobResult` — it reads the completed job's `summary` (`excitation_energies_eV`/`oscillator_strengths`), Gaussian-broadens them (`app/chemistry/spectrum.py`, headless `matplotlib.use("Agg")`), saves the image into that job's `data/jobs/<id>/` directory, then re-reads and re-writes `result.json` via `read_result`/`write_result` with an added `artifacts["uvvis_spectrum"]` path. It refuses outright (no plot, no job dirs touched) rather than rendering a flat/fabricated line when `oscillator_strengths` is missing, `None`, or all-zero — the exact situation for a PySCF `eom_ccsd`/`casscf` job or any `caspt2` job, per the paragraph above. `frontend/src/jobs/UvVisPanel.tsx` just displays whatever artifact path is on disk, mounted inside `JobDetailDrawer.tsx` like the MO-cube viewer for the same "don't rebuild on a polling tick" reason.

**The React molecule viewer (`frontend/src/molecule/MoleculeViewer.tsx`, `frontend/src/jobs/MoCubeViewer.tsx`) is a hand-rolled imperative wrapper around the `3dmol` npm package**, not a normal declarative component — the 3Dmol viewer instance and its model state live in a `useRef`, rebuilt only via an effect keyed on the molecule/cube data itself, because putting `$3Dmol.createViewer(...)` calls directly in the render path would rebuild the WebGL view (and discard camera rotation/zoom) on every unrelated re-render. It is read-only (numbered atom labels only, no click-to-select bond/angle/dihedral measurement) — an earlier version had that feature, ported from a prior Streamlit custom component, but it was dropped after surfacing more trouble than it was worth (see git history around the React rewrite for what that entailed). One non-obvious bug shaped the current implementation, confirmed by direct browser testing rather than reasoning from the 3Dmol/React docs alone: **`GLViewer` has no `destroy()`/`dispose()`/`remove()` method, and `createViewer()` unconditionally appends a new `<canvas>` (its own WebGL context) into the given container.** React 18 Strict Mode's dev-mode double-invoke of effects (mount→cleanup→remount) nulls the container ref *before* running the effect's cleanup function, even though the actual DOM container node is *not* torn down across that synthetic cycle — so a cleanup-only "clear the container" fix is silently a no-op, and the first mount's orphaned `<canvas>` is still sitting in the container when the second mount's `createViewer()` appends another one on top of it. Browsers cap the number of live WebGL contexts per page (commonly 8–16); repeated mount/unmount without fixing this (e.g. switching between conversations, collapsing/reopening a panel) exhausts that cap, and every new context after that silently fails to initialize — the viewer renders as a blank square with no error, which was a real user-reported bug. The actual fix: clear the container (`containerRef.current.innerHTML = ""`) unconditionally at the *start* of the init effect, before creating a new viewer, not just in the cleanup function — verified via debug instrumentation that live canvas count stays at exactly 1 across dozens of rapid mount/unmount cycles after this change, was 2+ (and growing) before it.

**MO cube visualization works identically across all three engines via a shared molden-parsing layer (`app/chemistry/jobs/molden.py`), but each engine reaches a correct cube through a different path — confirmed by point-sampling AO evaluation against native PySCF calculations at several off-axis points, not by inspection.** `pyscf.tools.molden.load()`'s return shape depends on whether the file has one MO section (restricted/ROHF — flat `mo_energy`/`mo_coeff`/`mo_occ` arrays) or two (genuinely unrestricted — alpha/beta as a 2-tuple), so every function in `molden.py` normalizes to a flat, 1-based, optionally spin-labeled orbital list up front. PySCF needs no round-trip for its own cubes (`cubegen.orbital` works directly off its own in-memory `mo_coeff`) but `run_mo_visualization` now also writes an `orbitals.molden` artifact anyway — purely so the lazy per-orbital endpoint below can treat all three engines uniformly instead of PySCF needing its own separate re-generation branch. `build_mf` in `pyscf_runner.py` only ever returns RHF/ROHF/RKS/ROKS (never true UHF/UKS), so its `orbital_table`'s flat `zip(mf.mo_energy, mf.mo_occ)` is always safe even though `molden.from_scf` would take the tuple-valued branch for a genuine UHF `mf`. BAGEL's real molden export (a `{"title": "print", "file": "...", "orbitals": true}` block appended after the `hf` block) round-trips exactly — AO evaluation matched a native PySCF calculation on the same geometry/basis to a ratio of 1.0 at every sampled point — and feeds `molden.py`'s `cube_for_orbital`/`orbital_table`. BAGEL's own native `"moprint"` block was tried first and rejected: its cubes turned out to be per-orbital electron *density* (`|ψ|²` — non-negative everywhere, a symmetric double lobe with a node at the center along the bond axis) rather than the signed wavefunction amplitude the two-isosurface (blue/red lobe) MO viewer needs, and it also carries no per-orbital energy table at all. ORCA's molden export (`orca_2mkl input -molden`) is the one case that does *not* round-trip despite looking fine on cheap checks — it parses without error, and both individual AOs and the target MO pass a naive self-overlap check (=1.0) — but point-sampling showed each AO column scaled by a different, shell-dependent constant relative to native PySCF evaluation of the same basis/geometry (~0.35x/1.1x/0.5–0.6x for different shell types), consistent with a contraction-coefficient normalization mismatch between the two programs' molden conventions (not a sign/ordering-only difference, which would show ratios of exactly ±1). ORCA's cubes instead come from `render_orbital_cube` in `orca_runner.py`, which drives `orca_plot` — ORCA's own native cube-file generator — interactively via piped stdin commands against a completed job's own `.gbw` file; verified correct via the same point-sampling technique, to within a few percent attributable to the cube's own finite grid spacing. `scratch.py`'s ORCA cleanup rule (`_ORCA_KEEP_NAMES`) now retains `input.gbw` for every completed ORCA job, not just ones submitted as `mo_visualization`, specifically so any completed ORCA job (e.g. inspecting orbital character behind a TDDFT/CASSCF excited state) can have orbitals rendered later on demand.

**ORCA's default `ORBITAL ENERGIES` output is silently truncated to the first 10 virtual orbitals** (a literal `"*Only the first 10 virtual orbitals were printed."` line), which would make `OrbitalTable.tsx` rows past HOMO+10 permanently unreachable — confirmed on a real def2-SVP water run (24 basis functions, only 16 rows printed by default). `mo_visualization`'s ORCA input (`build_input_text` in `orca_runner.py`) adds `! ... LargePrint` to force the full table, but `LargePrint` also prints a full MO coefficient matrix dump (`MOLECULAR ORBITALS (RHF, ROHF)`) immediately after the energies table with no blank line separating the two — the previous parser matched everything up to the next blank line in one regex, so it would have silently absorbed that unrelated section too. `_orbital_energy_rows` now scans row-by-row from the table header instead, stopping at the first line that doesn't match the four-column `NO OCC E(Eh) E(eV)` shape — which naturally skips both the truncation-notice line (on a non-`LargePrint` run) and the coefficient dump (on a `LargePrint` run) without needing to special-case either. This helper is shared with `_homo_lumo_gap`, used by every ORCA `single_point` job, not just `mo_visualization` — both call sites were re-verified against real runs after the rewrite, since the rewrite touched shared code with only one of its two callers directly in view at the time.

**Any orbital of a completed `mo_visualization` job can be rendered lazily on click, not just the ones eagerly rendered at submit time.** `POST /api/jobs/{job_id}/orbitals/{index}/cube` (`server/routes/jobs.py`) generates a cube the first time a given `(index, spin)` is requested — via `molden.cube_for_orbital` for PySCF/BAGEL, or `orca_runner.render_orbital_cube` against the retained `input.gbw` for ORCA — and caches the result into `result.json`'s `artifacts.cubes` under an `"idx{N}"`/`"idx{N}_{spin}"` key (distinct from the `"HOMO"`/`"LUMO"` keys written at job submission, so the two schemes never collide); a repeat request for the same orbital is then just a disk read via the existing `GET /api/jobs/{id}/artifacts/{key}` path. The new `frontend/src/jobs/OrbitalTable.tsx` renders the per-orbital `{index, spin, energy_eV, occupancy}` table every engine's `mo_visualization` summary now carries in the same shape (added to PySCF's `run_mo_visualization` to match what ORCA/BAGEL already produced), and its row clicks drive `MoCubeViewer.tsx` through a new controlled `orbitalSelection` prop — coexisting with the viewer's original HOMO/LUMO label dropdown, which explicitly clears `orbitalSelection` on use (via an `onClearOrbitalSelection` callback lifted to `JobDetailDrawer.tsx`) so a stale table selection can't get silently stuck outranking the dropdown. `MoCubeViewer.tsx` also now separates cube-text fetching from rendering into two effects: dragging the isoval slider re-renders instantly from the already-fetched cube text instead of re-fetching (and re-running `orca_plot`/`molden.py` server-side) on every tick, and the camera only re-frames (`zoomTo()`) when the underlying cube itself changed, not on every slider drag. The slider exists because cubes from `orca_plot`/`cubegen`/`molden.py` come from three different grid extents and orbital diffuseness — a single hardcoded isovalue (`0.04`) that suits a compact occupied water MO doesn't necessarily suit a diffuse virtual orbital on a larger basis.

**Orbital visualization is available on every completed `single_point`/`tddft`/`eom_ccsd`/`casscf`/`caspt2` job automatically — the user never has to submit a separate `mo_visualization` job.** `run_single_point`/`run_tddft`/`run_eom_ccsd` (PySCF and ORCA) and `run_casscf`/`run_caspt2` (PySCF, ORCA, BAGEL) always write a molden export (PySCF: `_write_molden_and_table` off the already-in-memory `mf`; ORCA: `! ... LargePrint` plus the existing `_orbital_table()` parser; BAGEL: the same `{"title": "print", "file": "orbitals.molden", "orbitals": true}` block `mo_visualization` already used, now appended to every `casscf`/`caspt2` input too) and an `orbital_table` in the summary, at negligible marginal cost since the wavefunction is already computed either way. `frontend/src/jobs/JobDetailDrawer.tsx` needed exactly one change for this to show up in the UI: the "Molecular orbitals" section was gated on `artifacts.cubes` being non-empty (true only for a job that pre-rendered specific orbitals at submit time, e.g. `mo_visualization`'s `orbital_indices`), so a `single_point` job — which now has an `orbital_table` but no pre-rendered cubes at all — would have silently never shown the section; the gate now also fires on `orbital_table` being present, and `MoCubeViewer`'s `cubeLabels` prop degrades to an empty dropdown in that case (harmless — `OrbitalTable.tsx` row clicks drive the same lazy per-orbital endpoint regardless of whether any cube was pre-rendered). CASSCF orbitals needed real verification, not just wiring: PySCF's `mc.mo_coeff` after a plain `.kernel()` are canonicalized MOs with integer 0/2 occupations, not natural orbitals — `molden.from_mcscf(mc, path, cas_natorb=True)` is what actually canonicalizes to natural orbitals via `mc.make_rdm1()` (state-averaged across all roots for `n_states > 1`, the standard shared-orbital-set choice for SA-CASSCF) and was confirmed by point-sampling AO values at several off-axis points against `mc.canonicalize(sort=True, cas_natorb=True)`'s own output directly (ratio 1.0 at every point) to give genuinely fractional active-space occupations (e.g. ~1.98/1.98/0.02/0.02 for a closed-shell CAS(4,4)) rather than the plain integer occupations a naive HF-style export would show. ORCA turned out to already print exactly the right table for free: a real CASSCF run with `LargePrint` showed only one `ORBITAL ENERGIES` block in the whole output, appearing *after* "CASSCF RESULTS"/"Final CASSCF energy" with genuinely fractional active-space occupations already — so the existing `_orbital_table()` needed no CASSCF-specific branch. BAGEL was the one real bug this surfaced: the first implementation appended the `print`/molden block last in the pipeline (after `smith`/caspt2, reasoning that CASPT2 doesn't reoptimize orbitals so placement shouldn't matter) and a real CAS(4,4)/cc-pVDZ CASPT2 run came back with every occupation flattened to integer 0/2 and every orbital energy at 0.0 — BAGEL's "current wavefunction" the print block reads from is no longer the CASSCF natural-orbital state once `smith` has run. Moving the `print` block to immediately after `casscf` (before any `smith` block is appended) fixed it, confirmed by rerunning the same CASPT2 job and seeing correct fractional occupations while `caspt2_energy_hartree` stayed bit-for-bit identical (a `print` block is a pure I/O side effect, so its position doesn't change the computed energy — only what "current wavefunction" it captures). Every engine's CASSCF/CASPT2 `orbital_table_note` says these are natural orbitals with real occupation numbers, not integer HF-style occupancies; BAGEL's note additionally flags that its molden export writes `energy_eV=0.0` for every active-space orbital specifically (confirmed in the raw `.molden` file, not a parsing gap) since BAGEL has no single-particle Fock eigenvalue for a multi-configurational active orbital the way ORCA/PySCF's CASSCF exports do. Adding `LargePrint` to ORCA's `single_point`/`tddft`/`eom_ccsd`/`casscf` inputs was verified with before/after diffs of the fully parsed summary (not just "still runs") on real water/STO-3G and water/def2-SVP-class jobs for every affected job type, each coming back byte-for-byte identical except for the new `orbital_table` key — `LargePrint`'s extra `MOLECULAR ORBITALS` coefficient dump lands after the sections `_FINAL_ENERGY`/`_homo_lumo_gap`/`_dominant_transitions_orca`/`_ELECTRIC_DIPOLE_SECTION`/`_CASSCF_BLOCK` all anchor on, so none of them shifted. For `tddft`/`eom_ccsd`, the table is explicitly labeled via `orbital_table_note` as the ground-state reference orbitals the excitations were built from, not excited-state-relaxed natural orbitals, so a user reading π→π* character off the table isn't misled about which orbitals they're looking at.

**Vibrational-mode animation and IR spectra work on ORCA/BAGEL `frequency` jobs too, not just PySCF's.** `ModeAnimationViewer.tsx`/`VibrationTable.tsx` and `plot_ir_spectrum`/`IrSpectrumInline.tsx` were originally PySCF-only (`pyscf.hessian.thermo.harmonic_analysis`'s `norm_mode`, shape `(n_modes, n_atoms, 3)`, is the only place a `normal_modes` array existed) — ORCA and BAGEL both print the same information as plain text, just in a different layout, verified against real water/HF/STO-3G runs on this machine before writing any regex (same discipline as every other engine-specific parser in this file). ORCA's `NORMAL MODES` section prints the full 3N×3N mass-*deweighted* Cartesian-displacement matrix (its own header text confirms the 1/sqrt(mass) mass-weighting has already been undone, i.e. these are real-space displacement vectors, not the mass-weighted Hessian eigenvectors) in blocks of up to 6 mode-columns with no blank line between blocks; BAGEL prints the equivalent under a section literally titled "...corresponding cartesian eigenvectors" — critically *not* the earlier "Mass Weighted Hessian Eigenvectors" section, which has an identically-shaped block layout but is the wrong physical quantity (would make heavier atoms visibly under-displace relative to lighter ones in the animation). Both engines' blocks are parsed by one shared structural helper, `orca_runner._parse_column_block_matrix` (imported into `bagel_runner.py` rather than duplicated, since the block-header/data-row shape is identical on both engines even though the surrounding page layout differs — BAGEL interleaves `Freq (cm-1)`/`IR Int. (km/mol)` rows between the header and the data rows, ORCA doesn't; the parser tolerates arbitrary non-matching lines between a header and its data rows, so both layouts work unchanged). ORCA additionally exposes an `IR SPECTRUM` table (parsed by `_ir_intensities_orca`) that BAGEL already had (`_HESSIAN_IR_ROW`, pre-existing) — PySCF computes neither IR intensities nor a dipole-derivative tensor in this app, so `ir_intensities_km_mol` stays ORCA/BAGEL-only, same asymmetry pattern as CASSCF oscillator strengths above. Both engines' `normal_modes`/`ir_intensities_km_mol` parsing degrades to `None` on any exception rather than failing the whole job (wrapped in `try/except` right at the call site in `run_frequency`'s `build_summary`) — a malformed section shouldn't take down an otherwise-successful frequency calculation's core frequency/thermochemistry results. `plot_ir_spectrum` (mirroring `plot_excited_state_spectrum`) and its matplotlib backend `render_ir_spectrum_plot` (`app/chemistry/spectrum.py`) drop modes with `|frequency| < 10 cm⁻¹` before broadening — both engines keep the 5-6 near-zero projected translational/rotational modes in their frequency lists (a deliberate, pre-existing choice so the two text-parsed engines stay index-aligned and consistent with each other), and including a literal 0.0 cm⁻¹ point would stretch the whole plot's x-axis to include a long dead zone before the first real vibration. The plot follows the conventional IR-spectroscopy display direction (high wavenumber on the left); `IrSpectrumInline.tsx`'s client-side preview (mirroring `UvVisSpectrumInline.tsx`) matches this via a simple negation of the x-axis, not a re-sort, since (unlike UV/Vis's nonlinear eV→nm conversion) wavenumber needs no unit transform, so negation alone preserves monotonicity.

**`generate_job_input`/`submit_job` mechanically query the manuals/reference-docs KB on every call, not just when the LLM decides to.** `search_knowledge_base` (`app/rag/query_tool.py`) is a normal LLM-discretionary tool with only a soft system-prompt instruction to use it for exact syntax — nothing forced the agent to actually call it before generating input, and in practice it didn't: a real job (DFT geometry optimization on uracil) was submitted with the PySCF basis string `"6-31gd"`, which PySCF doesn't recognize (its Pople-basis parser only accepts `*`/`**` suffixes or a parenthesized `(d)`, e.g. `"6-31g(d)"`/`"6-31g*"` — `"6-31gd"` isn't a registered alias), and the job failed at runtime with an unhelpful raw `KeyError` traceback instead of being caught earlier. Since this codebase already treats "left to the LLM's discretion" as an unreliable mechanism for anything safety- or correctness-critical (see the CASSCF oscillator-strength routing note above), the fix was to make the KB lookup structural: `_build_spec_or_error` in `tools.py` (the function shared by both tools) now always calls `_kb_context_for_job()`, which runs a `similarity_search` filtered to `doc_type="manual"` using the engine/job_type/method/functional/basis as the query, and returns whatever it finds (or `""` on an empty/unreachable store — best-effort, not a hard gate). The result is threaded through both call sites: `generate_job_input` appends it to the ToolMessage the LLM sees (with an instruction to cross-check parameters against it), and `submit_job` adds it to the `interrupt()` payload so `frontend/src/approvals/JobApprovalCard.tsx` shows it under a "Manual/reference excerpts consulted" section on the human approval card — the last checkpoint before a job actually runs, and the one place this doesn't depend on the LLM reading anything at all. This is retrieval-and-surface, not verification: nothing parses the retrieved text or blocks a bad parameter automatically, and the underlying KB content quality varies by engine (ORCA/BAGEL's crawled manuals document keyword syntax directly; PySCF's KB is generated from installed-package docstrings, which cover class/method signatures well but don't document basis-set naming conventions at all, so KB grounding is weaker for exactly the class of error that motivated this — confirmed by testing `_kb_context_for_job` against real queries). This manual-only filter is deliberately *not* extended to `doc_type="paper"` or to the academic-literature tool described below — this lookup exists purely for software syntax/keyword grounding, and papers would add surface to the approval card with no correctness gain for that specific check. Conceptual/molecular-background questions are a separate, prompt-guided knowledge-source category (see `app/agent/prompts.py`'s `SYSTEM_PROMPT` and the paragraph below on `search_academic_literature`).

**`_build_spec_or_error` also mechanically corrects two specific, previously-observed parameter typos before validation runs, rather than relying on the KB lookup above or the LLM's own retry loop to eventually notice.** `app/chemistry/jobs/param_normalize.py`'s `normalize_method`/`normalize_basis` run first and rewrite `params["method"]`/`params["basis"]` in place when (and only when) the value doesn't already validate. `normalize_method` covers the fact that this app's `method` parameter only ever means `"hf"` or `"dft"` everywhere it's consumed (`pyscf_runner.build_mf`, `orca_runner._method_line`, `bagel_runner`'s hf-only paths all raise on anything else — restricted vs. unrestricted reference is chosen automatically from the molecule's spin, never exposed as a separate choice) — so RHF/UHF/ROHF and typos of them (an explicit alias table plus a tight `difflib` fuzzy fallback, cutoff 0.75, single best match only) all collapse to `"hf"`. `normalize_basis` targets exactly the `"6-31gd"`-shaped bug the paragraph above already documents: a Pople basis name (`\d+-\d{2,3}\+{0,2}g`) with a polarization/diffuse suffix glued on without parentheses. The fix is a single targeted rewrite (wrap the suffix in parens) rather than a general basis-name fuzzer, and it's re-verified against PySCF's own `gto.basis.load()` before being accepted — necessary because PySCF's parser was found to silently accept *and drop* an unrecognized parenthesized suffix rather than raising (`"6-31G(zzz)"` loads "successfully" as plain unpolarized 6-31G), which would otherwise let this same repair mask a nonsense suffix instead of catching one; the suffix pattern is therefore restricted to digits plus the literal angular-momentum letters that appear in real polarization shorthand (`[0-9dfgpDFGP]+`), not a bare alphanumeric wildcard. This runs before `default_engine()` resolves which engine the job will actually use, so the rewrite is applied uniformly regardless of destination engine, but it's only actually *verified* against PySCF's parser — checked directly against BAGEL's own install (`share/6-31g.json` etc.), its basis files don't name polarization variants with a parenthesized suffix the way PySCF/ORCA do at all, so for a BAGEL-bound job this rewrite is functionally neutral (a string BAGEL would've rejected stays rejected either way) rather than a confirmed fix; ORCA is believed compatible with the same Pople convention but that hasn't been separately checked against ORCA's own parser the way the rest of this file's claims are. Both correctors are deliberately narrow: an unrecognized value (a genuinely different/unsupported method like `"mp2"`, or a basis typo outside this one glued-suffix pattern) is left untouched and falls through to the existing error path unchanged, never silently guessed at. Corrections are surfaced, not applied invisibly — threaded through `_build_spec_or_error`'s return alongside `kb_context`, appended to `generate_job_input`'s ToolMessage, and added to `submit_job`'s `interrupt()` payload as `param_corrections` so `JobApprovalCard.tsx` shows an "Auto-corrected: ..." banner before the human approves.

**A `job_type='custom'` job lets the agent run an arbitrary ORCA/BAGEL calculation this app has no registered job_type/parser for, through the exact same approval-card + background-execution pipeline as every other job, rather than needing a hard-coded job_type for every ORCA/BAGEL feature this app might ever want to expose.** The agent composes the complete literal input text itself (`raw_input_text`) instead of this app building it from structured params — `_build_custom_spec_or_error` in `tools.py` pops it straight into `spec.params["_raw_input"]` and uses it verbatim as the preview, entirely bypassing `preview.py`'s per-engine `build_input_text` dispatch (which stays a closed `if job_type == "...": ... raise ValueError` chain, unmodified, for every other job_type). This turned out to need almost no new machinery: `JobManager.submit`/the worker subprocess dispatch are already generic over `(method, engine)` pairs (only `orca_worker.py`/`bagel_worker.py`'s `DISPATCH` dicts needed a `"custom": run_custom` entry each), `validate_input` doesn't look at job_type at all, and — confirmed by reading `JobApprovalCard.tsx`/`JobDetailDrawer.tsx` directly rather than assuming — the approval card's editable-textarea branching is keyed purely on `engine` (`EDITABLE_ENGINES = {"orca", "bagel"}`), and the drawer's "Molecular orbitals"/spectrum/vibration sections are all independently gated on specific `summary` keys being present, so a job whose `summary` is deliberately near-empty (just a `note` + `raw_output_tail`, no structured fields) already degrades on its own to exactly "geometry + raw input/raw output only," with zero frontend changes needed beyond a new non-blocking-warnings banner (see below). `orca_runner.run_custom`/`bagel_runner.run_custom` do no output parsing (there's no job_type-specific parser to parse *with*) — BAGEL's `_run_bagel` already only checks the process returncode (no content marker), so it's reused directly, but ORCA's existing `_write_and_run` hard-requires `"FINAL SINGLE POINT ENERGY"` in the output, a marker specific to the SCF-based job_types this app otherwise knows about and not guaranteed for an arbitrary calculation type (e.g. NEB/IRC) — a separate `_write_and_run_generic` checks for `"ORCA TERMINATED NORMALLY"` instead (confirmed calculation-type-agnostic: present in 30 of 32 real `output.out` files under `data/jobs/` on this machine, the other 2 being genuine failures — an aborted SCF and a malformed input — that legitimately never printed it either).

Structural validation (`validate.py`'s `validate_orca_input`/`validate_bagel_input`) is deliberately **non-blocking** for `custom`, at both the composition step and the hand-edit-before-approval step — unlike every other job_type's hand-edit path (which starts from a *generated*, standard-geometry input, so a validation failure there means something broke a previously-valid file), a custom job's entire reason to exist is carrying ORCA/BAGEL syntax this app's validator was never built to recognize (`* xyzfile <charge> <mult> geom.xyz` instead of an inline `* xyz` block, a `%coords` block, a multi-step `$new_job` stack) — hard-blocking on it would defeat the feature's own premise. `_build_spec_or_error`'s return tuple gained a `warnings: list[str]` element for this (always `[]` for every other job_type) rather than reusing the existing `param_notes`/`param_corrections` channel, since that channel's UI banner literally reads "Auto-corrected: ...", which would misrepresent a validation complaint as a correction that was actually made — surfaced instead as its own "Structural check found possible issues (not blocking)" banner in `JobApprovalCard.tsx`. A custom job has no `method`/`basis`/`functional` params to build a KB query from the way `_kb_context_for_job` does for every other job_type (that would just search `"orca custom"`/`"bagel custom"` and surface semantically random manual chunks labeled as grounding), so `calculation_description` — an optional short free-text label the agent supplies, e.g. "NEB transition-state search" — doubles as both the KB query text and (once approved) the job's display label in the Job Manager, confirmed via a real live-browser submission that this needed one extra step beyond just setting `JobSpec.label`: `_job_row` (`server/routes/jobs.py`) computes its displayed `label` as `meta.get("label") or auto_job_name(spec)`, reading only the separate, mutable `meta.json` (rename-endpoint-owned) — `spec.json`'s own write-once `label` field, which is all `_build_custom_spec_or_error` sets, is never read there at all, so the job showed up generically as e.g. "water custom (ORCA)" regardless of what `calculation_description` said. `spec.label` still round-trips correctly through the interrupt/resume boundary (it's part of `spec.to_dict()` like every other field), so the fix reads it back as `approved_spec.label` after a successful `submit()` and writes it into `meta.json` via `write_meta(job_id, {"label": approved_spec.label})` — using the real, final job_id from after resume (not the discarded provisional one from before it) — for `custom` jobs only, mirroring exactly what the manual-rename endpoint already does. The pre-existing auto-retry carry-forward loop in `submit_job` (see the failed-job-retry section below) explicitly skips any key starting with `_`, but `raw_input_text` is popped out of `params` and re-stored as `_raw_input` before a spec is ever built — so without an explicit extra carry-forward line for it, a retry that didn't re-supply corrected text itself would hit "still missing: raw_input_text" instead of ever reaching another approval card.

**Config is centralized in `app/config.py`**, all overridable via `QC_AGENT_*` env vars: `LLM_MODEL` (default `qwen3:30b`), `LLM_BASE_URL`/`EMBEDDING_MODEL` (Ollama), `ORCA_BIN`/`BAGEL_BIN`/`BAGEL_ONEAPI_SETVARS`, `N_CORES`, `MAX_CONCURRENT_JOBS`. The LLM client in `app/agent/graph.py` sets `timeout=150, max_retries=0, max_tokens=1024` — defensive bounds for a locally-hosted model, not a fix for any specific known bug (an earlier multi-minute stall was misdiagnosed as model "thinking" behavior; the real cause was the missing `NotRequired` above, which made every tool call fail and loop).

**`JobManager._wait_for_resources` (`app/chemistry/jobs/base.py`) gates job *admission* on the HOST's real headroom, not just this app's own subprocesses — this machine is genuinely shared with other tenants/processes outside this app's control (confirmed by the user, not assumed).** An earlier version only tracked this app's own job subprocess trees (`psutil.Process.cpu_percent` summed over each job's pid tree, normalized by `N_CORES`) — deliberately avoiding host-wide `psutil.cpu_percent()` because it read near-zero even under full load on this app's own cores, diluted across the host's full 255-logical-CPU count. That app-scoped view was blind to load from *other* tenants: another process saturating the shared host wouldn't move this app's own reading at all, so a new `N_CORES`-core job would still get dispatched regardless, compounding load on a machine something else was already stressing. The gate now checks two things every ~1s poll, both via a single blocking `_host_cpu_snapshot()` call (`psutil.cpu_percent(interval=1.0, percpu=True)`, which needs no priming/baseline the way the old per-pid `interval=None` tracking did, and whose 1s block doubles as the loop's own pacing): (1) host-wide aggregate CPU and memory below `MAX_CPU_PERCENT`/`MAX_MEM_PERCENT` — a coarse "is the whole host in distress" backstop, now meaning "% average across all 255 logical CPUs," a much higher bar than the old app-scoped 80%-of-8-cores reading (reaching it takes ~200+ cores near-saturated at once); (2) at least `N_CORES` individual logical cores currently idle (`CORE_IDLE_THRESHOLD_PERCENT`, default 20% busy) — kept as a separate condition rather than relying on the aggregate alone, since a low aggregate can hide uneven load (the specific cores this job would land on could still be busy) just as easily as a merely-moderate aggregate can hide plenty of idle capacity elsewhere; in practice this idle-core check is what does the meaningful gatekeeping at ordinary contention levels. Verified live: submitting an ORCA CASSCF job followed immediately by a BAGEL CASSCF job under the old app-scoped gate left BAGEL `pending` ("waiting for CPU/memory headroom (cpu 100%, mem 4%)") for ORCA's entire multi-minute runtime, purely because ORCA was using 100% of this app's *own* 8-core budget; under the new host-wide gate, repeating the identical scenario on the same (otherwise idle) host let both jobs start within milliseconds of each other and complete concurrently, since the wider host had ample idle capacity regardless of what this app's own jobs were doing.

Deliberately **not** layered with an *additional* app-scoped "this app's own concurrently-running jobs never collectively exceed `N_CORES`" cap, even though `N_CORES=8` turned out to be a voluntary courtesy convention rather than anything kernel-enforced (see the `_detect_usable_cores()` note above) — meaning nothing stops two of this app's own `N_CORES`-sized jobs from running at once and, in aggregate, using more than `N_CORES` real cores when the host has room. This was a real design fork, not an oversight: keeping such a cap was considered and explicitly rejected after presenting the tradeoff (self-limit to a fixed courtesy ceiling even on an idle host, vs. trust the host-wide gate alone and get higher throughput when the host is quiet) — the latter was the deliberate choice on this deployment. `CORE_IDLE_THRESHOLD_PERCENT` and the two `MAX_*_PERCENT` constants are all independently `QC_AGENT_*`-overridable if that trade-off should be revisited later.

**`JobManager` reconciles orphaned jobs on construction, because a job's worker subprocess deliberately outlives its parent backend process, but the code that finalizes `status.json` did not.** A job's worker runs fully detached (`start_new_session=True`, its own process group) specifically so a crash or restart of the FastAPI backend can never take down an in-progress calculation — but the *only* thing that ever wrote the final `write_status(job_id, result["status"], "done")` call was `_run_inner`'s own blocking `proc.wait()`, running on a thread inside that same backend process. Restarting the backend (routine in this dev workflow — no autoreload) while a job was still running left that thread, and the whole in-memory `JobManager` instance including `self._procs`, gone — but the orphaned worker kept computing and wrote a fully correct `result.json` on its own once done, with nothing left alive to sync `status.json` to match. This is not hypothetical: reproduced for real when an in-progress ORCA CASSCF job's backend was restarted mid-run — `result.json` ended up with a complete `"completed"` summary while `status.json` stayed stuck reporting `"running"` forever, and both `cancel()` (looks for a live `Popen` in `self._procs`, empty in the new process, so it silently returned `False`) and `DELETE /api/jobs/{id}` (refuses to touch a non-terminal job) became permanently unable to touch it. The fix, in `base.py`: every worker spawn now also persists its pid and `psutil`-reported `create_time` into the job's `meta.json` (via the existing `write_meta`, previously only used for the user-settable display label); `JobManager.__init__` calls a new `_reconcile_orphaned_jobs()` once, which walks every job still on disk as `pending`/`running` (nothing a *fresh* instance could have legitimately left in that state itself) and handles three cases — `result.json` already terminal (sync `status.json` to match; this was the exact reproduced bug), a worker pid that's still alive and identity-verified against the recorded `create_time` (`_pid_is_same_process`, guarding against pid reuse — re-attach it via a `_watch_orphan_worker` thread on the same executor, polling with `psutil.Process.wait()` since it's not this process's child so a real `Popen.wait()` isn't available, and register it in a new `self._orphan_pids` dict so `cancel()` can still reach it), or neither (mark `"failed"` with an explanation rather than leaving it stuck forever). Verified against the real stuck ORCA job (correctly synced to `"completed"`) plus two synthetic cases confirming the live-orphan path end-to-end: a still-running process gets re-attached, `cancel()` successfully kills its real process group, and the watcher thread finalizes status to `"cancelled"`; a genuinely dead orphan with no result gets marked `"failed"` instead of staying stuck.

**`neb_ts` (Nudged Elastic Band transition-state search) is ORCA-only and runs as a SINGLE job, unlike `pes_scan`'s per-image sub-job architecture — ORCA parallelizes the path-image energy/gradient evaluations itself via `%pal`, so there's no orchestration for this app to do beyond submitting one ordinary job.** The product (end) geometry reuses `pes_scan`'s existing two-endpoint plumbing verbatim — `set_pes_scan_endpoint`/`state["pes_scan_end_molecule"]` — rather than adding a NEB-specific tool/state slot, since it's the same "second endpoint geometry" concept; `_build_neb_ts_spec_or_error` in `tools.py` is the only new dispatch branch in `_build_spec_or_error`, mirroring `_build_scan_spec_or_error`/`_build_custom_spec_or_error`'s existing pattern. `preopt` (whether to pre-optimize the two endpoints first, ORCA's `PreOpt` keyword) is a required param with no default specifically so the agent is forced to ask the user rather than silently picking a value, per explicit instruction — the same "required forces elicitation" mechanism `n_states`/`coordinate` already use elsewhere, not new machinery. `target_state` (an excited-state PES to run the search on, via a `%tddft`/`IRoot` block) is optional and unset means ground-state; setting it auto-raises `n_states`/`NRoots` to at least `target_state` if the caller didn't set it explicitly.

Every file-naming/behavior claim below was verified against real ORCA 6.1.1 NEB-TS runs on this machine (a tiny HF/STO-3G NH₃-inversion test), not the manual alone, following this codebase's established practice for every other engine-specific parser. ORCA writes one `.gbw` per path image (`input_im{N}.gbw`, N = 0..n_images_total-1, in the same order as the `PATH SUMMARY` table's numbered rows) plus a final `input.gbw` that — confirmed by comparing mtimes — ends up holding whichever calculation ran LAST, which for a converged NEB-TS run is the TS-optimization step's own wavefunction, not any path image's. `input_MEP_trj.xyz` ("final converged MEP trajectory" per the manual) is written exactly ONCE, when the NEB/CI-NEB part itself converges, and is NOT updated again once the subsequent TS-optimization refinement runs further — confirmed directly: its mtime stayed frozen while `input_NEB-TS_converged.xyz` (written afterward) got a later one. This matters because it means `input_MEP_trj.xyz` is NOT a live "current state of the run" file despite its name suggesting otherwise; `input_MEP_ALL_trj.xyz` is the one file that genuinely grows every NEB iteration (confirmed: its size increased between two polls of a still-running job, before `input_MEP_trj.xyz` even existed) — so that file, chunked into `n_images_total`-frame groups via the new `split_xyz_frames` helper in `orca_runner.py`, is what a live "current iteration" viewer must read (`GET /api/jobs/{id}/neb_frames_live` in `server/routes/jobs.py`, a live disk read on every call like the `/log` tail route, not cached). ORCA prints two different `PATH SUMMARY` tables depending on how far the run got — the plain one (6 columns incl. `Dist.(Ang.)`, no TS row) once NEB/CI-NEB itself converges, and `PATH SUMMARY FOR NEB-TS` (5 columns, includes a distinguished `TS` row near the climbing image) once the TS-optimization step also converges — `_neb_path_summary` in `orca_runner.py` prefers the latter but falls back to the former so a run where NEB converged but TS refinement didn't still yields a usable path instead of nothing; both are matched by scanning row-by-row from the LAST occurrence of their own column header (same technique as `_orbital_energy_rows`' `last=True` mode below), never a first-match `re.search`, since ORCA can print the plain table once and the `FOR NEB-TS` one again afterward. `_orbital_energy_rows`/`_orbital_table` gained a `last: bool` parameter for the same reason applied to the "ORBITAL ENERGIES" block specifically: a real run showed TWO such blocks (an early path image's own SCF, then the final TS-optimized wavefunction's) — `run_neb_ts` always requests `last=True` so the reference-orbital table shown in the UI is the TS structure's, not an arbitrary early image's.

A non-converged run comes back `status="completed"` with `neb_converged`/`ts_converged` flags in the summary, NOT `status="failed"` — deliberately, since `write_result`'s `artifacts` dict is empty on a failed job and `scratch.py`'s cleanup rule only protects files declared there, so marking a merely-not-yet-converged run as "failed" would silently delete the one thing worth inspecting (the partial path). `_write_and_run_generic`'s `"ORCA TERMINATED NORMALLY"` check (the same generic marker `run_custom` uses, not the job-type-specific `"FINAL SINGLE POINT ENERGY"` check every other job_type's runner uses) is still the genuine failure gate — a real crash/non-zero exit still fails the job normally. All per-image `.gbw` files, the combined frame file, and the converged-path/TS-geometry files are declared in the job's own `artifacts` dict (nested under `image_gbw`, walked recursively by `scratch.py`'s `_artifact_filenames`) specifically so they survive scratch cleanup — no changes to `scratch.py` itself were needed, since its allowlist rule already protects anything a job declares as an artifact.

`render_orbital_cube` (`orca_runner.py`, also used by `mo_visualization` and the lazy per-orbital cube endpoint) gained a `gbw_filename` parameter so a specific path image's orbitals can be rendered on demand — this required deriving the expected cube-file path from the GBW file's own stem rather than a hardcoded `"input"` prefix, confirmed empirically (`orca_plot input_im3.gbw -i` writes `input_im3.mo0a.cube`, not `input.mo0a.cube` — orca_plot names its output after whichever GBW file it was actually given). `POST /api/jobs/{id}/orbitals/{index}/cube` (`server/routes/jobs.py`) gained a matching `gbw` query parameter, strictly allowlist-validated against `^input(_im\d+)?\.gbw$` before it's ever used to build a filesystem path, since it's client-supplied. There is deliberately no per-frame orbital ENERGY table (only cube rendering) — ORCA has no per-image "ORBITAL ENERGIES" printout to build one from without adding a job-type-specific keyword per image, which wasn't asked for; the frontend's `NebFrameViewer.tsx` exposes a plain numeric "orbital #" input instead (defaulting to the TS frame's own HOMO index, since electron count is identical across every image of the same molecule).

The frame slider (`NebFrameViewer.tsx`) shows a different ordering than ORCA's own image numbering, by design: for a completed job, frame 0 is always the refined TS structure (`input_NEB-TS_converged.xyz`, falling back to `input_NEB-CI_converged.xyz`/`input_NEB-HEI_converged.xyz` if the TS-optimization step never got there), followed by the converged path's numbered images 0..N-1 — built server-side as a single combined `neb_frames` artifact via plain text concatenation (both source files are already valid standalone xmol multi-frame blocks, so no structured parse is needed to combine them). While the job is still running, the same component instead polls the live-frames route above every few seconds and shows the current iteration's numbered images with no TS frame (none exists yet). The reaction-path plot (`render_neb_plot` in `app/chemistry/spectrum.py`, `NebEnergyPlot.tsx`) only ever appears once the job completes — unlike `pes_scan`'s `ScanPlot`, there's no incrementally-updated energy series to draw live for a single opaque ORCA job — and draws the TS point as a distinct marker at the climbing-image's index rather than inventing a fractional x-position for it, since the TS-optimization step moves off that image's exact geometry and has no true position of its own on the path's x-axis.

PySCF has no native NEB/NEB-TS implementation, and this app doesn't build one — `neb_ts`'s `ALLOWED_ENGINES` is `{"orca"}` only. Feasibility was assessed, not just assumed: `interpolate.py`'s existing `idpp_path` (already used by `pes_scan`'s two-endpoint mode) would supply the initial path, `ase.mep.NEB(climb=True)` plus a small custom `ase.calculators.calculator.Calculator` wrapping PySCF's own SCF+gradient (reusing `pyscf_runner.build_mf`) would do the CI-NEB relaxation, and `pyscf.geomopt.geometric_solver.optimize(mf, transition=True, ...)` — confirmed directly that `transition` is a real, already-supported kwarg via geomeTRIC's `OptParams` — would refine the climbing image into an actual TS afterward, reusing the exact same optimizer this app already uses for `geometry_optimization`. This was deliberately not implemented in the same pass as the ORCA path: it would need its own hand-rolled convergence criteria (no engine-native machinery to lean on, unlike ORCA) and would run serial per-image PySCF SCF+gradient evaluations with no equivalent to ORCA's `%pal` image-level parallelism, so it's a genuinely slower, less mature path that deserves its own implementation and verification pass rather than being rushed alongside the ORCA one.

## Knowledge base seeding

`scripts/seed_knowledge_base.py` crawls the BAGEL and ORCA manuals and generates PySCF reference docs from the *installed* `pyscf` package's docstrings (194 sources, ~4000 chunks total). PySCF is deliberately not scraped from pyscf.org — its `robots.txt` explicitly disallows `ClaudeBot` (`Content-Signal: ai-train=no`) — so `extract_pyscf_docs()` walks `inspect.getdoc()` over the key classes instead. Watch for dispatcher functions there: `mcscf.CASSCF`, `mp.MP2`, and `tdscf.TDA` at the top level are runtime dispatchers with *no docstring of their own* (0 chars) — the real content lives on the concrete classes they resolve to (`mcscf.mc1step.CASSCF`, `mp.mp2.MP2`, `tdscf.rhf.TDA`), so always extract from those, not the dispatcher. The crawler also force-corrects encoding via `apparent_encoding` when a server omits `charset` in `Content-Type` — `requests` otherwise silently falls back to ISO-8859-1 and mangles curly quotes/em-dashes (hit this on the ORCA manual).

## Automatic failed-job troubleshooting and retry

**A failed job triggers an automatic investigate-and-retry cycle, but the retry budget is enforced by code, not by the LLM counting its own attempts.** `app/agent/job_watcher.py` — a background thread started once at server startup, walking every conversation in the registry rather than being tied to any particular browser tab or request (see its module docstring for why: a closed tab must not silently stop auto-retry, and two open tabs on the same conversation must not both inject the same retry) — branches on status: a failed job gets a system notice instructing the agent to call `check_job_status`, then `search_knowledge_base(doc_type="manual")` and (if that's insufficient) the `web_search` tool (`app/agent/web_search.py`, DuckDuckGo via the `ddgs` package) — deliberately not `search_academic_literature`, since that tool covers published papers, not software error messages or syntax (see the knowledge-hierarchy paragraph below) — then call `submit_job` again with corrected parameters and `retry_of_job_id` set to the failed job's id — which still pauses on `interrupt()` for human approval exactly like any other `submit_job` call, so "the agent silently reruns a job with different parameters" is never possible; the human always sees the diff before it runs (the approval card shows a "🔁 Retry attempt N of M" banner and the corrected parameters). The budget cap (`MAX_AUTO_RETRIES = 3` in `app/chemistry/jobs/base.py`) is *not* read from anything the LLM supplies: `count_failed_in_chain()` walks a retry chain backward on disk via each job's `params["_retried_from"]` (written by `submit_job` itself when `retry_of_job_id` is passed) and counts how many jobs in it currently have `status == "failed"`, and `job_watcher.py` calls this directly before deciding which notice to send — an "auto-retry" notice below the cap, or a "stop and explain, do not retry" notice at/above it. This split exists because an LLM-tracked counter keyed on an optional argument it might simply omit resets to zero for free, which is exactly the "prompt-dependent behavior" this codebase has already been burned by once (see the `NotRequired` note above) — `submit_job`'s own `_retry_count` bookkeeping is provenance for the approval card's display only, never the gate. `read_spec()` (the same file's `read_status`/`read_result` pattern) returns `None` rather than raising on a missing/corrupt `spec.json`, since it's called from `submit_job`'s pre-`interrupt()` code path, which re-executes in full on every resume — an exception there kills the approval click outright rather than being caught into a `ToolMessage` (see the `submit_job` architecture note above). `check_job_status` also now includes the failed job's original `job_type`/`engine`/params in its report (previously just the raw traceback) — confirmed via direct testing to matter in practice: without it, the model correctly identified the right basis-set fix from the KB context but then guessed the wrong `job_type` for the retry (since nothing told it what the original job actually was) and never got as far as a corrected approval card.

**Knowledge access is task-dependent, not one undifferentiated pool.** The agent has four sources — the mechanical manuals-only KB lookup above (input prep), `search_knowledge_base` (LLM-discretionary, filterable by `doc_type` — `"manual"` or `"paper"`), `search_academic_literature` (`app/agent/scholar_search.py`, wraps the Semantic Scholar Graph API), and `web_search` — and `app/agent/prompts.py`'s `SYSTEM_PROMPT` gives each a distinct ordered hierarchy keyed to a recognizable situation (preparing a job input, troubleshooting a failed job, answering a general chemistry/method/active-space question, or writing a new tool/parser) rather than one flat "use this when relevant" instruction, since the four situations call for genuinely different sources and mixing them risks e.g. surfacing a software manual snippet for a chemistry-judgment question. `search_academic_literature` stands in for "Google Scholar," which has no official/free API and would otherwise require unreliable scraping (e.g. the `scholarly` package, prone to CAPTCHA blocks): it hits Semantic Scholar's `/graph/v1/paper/search/bulk` endpoint specifically, not `/paper/search` — confirmed empirically that the latter (relevance-ranked, no `sort` param) returns `429 Too Many Requests` repeatedly on the shared unauthenticated pool, while `bulk` both fared better and is the only endpoint supporting `sort=citationCount:desc` (the tool's `mode="seminal"`) or `sort=publicationDate:desc` (`mode="latest"`). Reliable day-to-day use likely needs a free API key (`QC_AGENT_SEMANTIC_SCHOLAR_API_KEY`) — the tool degrades gracefully without one (a `429` response returns an explanatory string telling the agent to fall back to `web_search` rather than retrying), so this isn't a hard blocker, just an expected-in-practice condition. Bulk's query syntax is literal boolean AND/OR of bare/quoted tokens, not semantic search, which is a real usability trap confirmed by direct testing: a natural multi-word question (e.g. "what active space should I use for CASSCF calculations of retinal photoisomerization excited states") returns zero hits since every bare word is ANDed together, while unquoted common words (`active space`) match hundreds of irrelevant papers by loose word overlap — only a query built from a few double-quoted, distinctive multi-word technical terms (`"active space" "CASSCF" "retinal"`) returns a clean, relevant result set. This is enforced entirely via the tool's own docstring contract (with explicit good/bad examples), the same way `doc_type` selection on `search_knowledge_base` is already prompt-guided rather than code-mediated — there is no query-rewriting layer.

## Known limitations

- `pes_scan`'s two-endpoint mode (`_liic_cartesian` in `pyscf_runner.py`) does Cartesian interpolation between structures, not true internal-coordinate LIIC. The single-coordinate scan mode (bond/angle/dihedral via `_internal_coordinate_scan`) is proper internal-coordinate manipulation via RDKit's `rdMolTransforms`.
- `/data` is at ~96% full. Job artifacts (including MO cube files, more relevant since every `single_point`/`tddft`/`eom_ccsd`/`casscf`/`caspt2` job writes a molden export by default — see the architecture note above, not just `mo_visualization` jobs) are capped at 100GB total via `app/chemistry/jobs/quota.py`, and knowledge-base storage (the Chroma vector store plus uploaded/pasted/scraped-via-URL source files) is capped at 10GB total via `app/rag/quota.py` — both enforced at write time (job submission / KB ingestion respectively), evicting oldest-first, and both deliberately spare content they didn't create the growth problem for (a pending/running job, or a pre-seeded manual under `data/scraped/`).
- Automatic orbital visualization (see the architecture note above) does not extend to `geometry_optimization`, `frequency`, or `pes_scan` — those job types don't call the molden-export helpers, so their completed jobs still show no "Molecular orbitals" section. This was a deliberate scope boundary (matching what was actually asked for), not an oversight; extending it would mean deciding which geometry's orbitals to export for a multi-step optimization/scan.
- BAGEL's standalone `casscf` job type and `pes_scan` driven through the chat agent (rather than called directly) are less thoroughly tested than the other paths.
- `neb_ts` is ORCA-only (PySCF has no native NEB implementation and this app doesn't build one — see the architecture note above for the feasibility assessment and what a PySCF path would actually need). There is no per-image orbital energy table, only lazy cube rendering per frame (ORCA prints no per-image "ORBITAL ENERGIES" section without a job-type-specific keyword addition this app doesn't make). Retaining every path image's own `.gbw` file (needed for the per-frame orbital viewer) is a real, uncapped-per-job storage cost on top of the usual molden export — at `def2-SVP`-class basis sets on a real multi-atom reaction this can be tens of MB per image, not the ~1MB seen on the tiny STO-3G test this feature was verified against; `quota.py`'s 100GB cap still applies (oldest-job-first eviction), but a single large `neb_ts` job can now consume noticeably more of that budget than most other job types.
- `neb_ts`'s excited-state path (`target_state`) is less thoroughly verified than the ground-state path. The ground-state path (input generation, `PATH SUMMARY FOR NEB-TS` parsing, TS/CI row detection, the reaction-path plot, per-frame geometries and orbitals) was confirmed end-to-end against multiple real converged ORCA runs. For `target_state`, two real runs confirmed the `%tddft`/`IRoot` block is correctly generated and genuinely drives ORCA through real per-iteration TDDFT-gradient NEB steps (visible in the output's "Energies of ground and excited states of the entire path" table) and that a real ORCA-side rejection (`"No barrier was found. Skipping NEB-TS run here."`, exit code 2, no `"ORCA TERMINATED NORMALLY"`) is correctly surfaced as a failed job rather than mishandled — but neither run reached a converged excited-state TS (the specific NH₃-inversion-mirror test geometry used has no real barrier on S1, a property of that toy test case, not a bug). This means the exact semantics of the `PATH SUMMARY`/`PATH SUMMARY FOR NEB-TS` energy column on a *successfully converged* excited-state run (whether it reports the target state's own energy or the ground state's, per the manual's example table having separate `E0`/`Root N` columns) were not directly confirmed against real output — treat `target_state` results with that in mind until checked against a real reaction with an actual excited-state barrier.
- Hand-editing the approval-card input is only available for ORCA and BAGEL, not PySCF (no literal input file to edit — see the architecture note above). Edited-input validation is structural/keyword sanity checking, not a real dry-run (neither engine offers one); a syntactically valid edit can still fail chemically or fail to parse afterward.
- Oscillator strengths for CASSCF (via `want_oscillator_strengths=True`) and EOM-CCSD are only ever available via ORCA in this app — PySCF and BAGEL report excitation energies only for these methods, and CASPT2 (BAGEL-only, since ORCA has no CASPT2) is energies-only with no engine-of-choice workaround. `plot_excited_state_spectrum` refuses cleanly in these cases rather than plotting a flat/fabricated spectrum.
- No general pre-flight basis-set/keyword *validator* exists for ORCA/BAGEL/PySCF beyond the approval-card's structural sanity checks (`validate.py`) and `param_normalize.py`'s two narrow, specific correctors (method-name aliasing, one Pople-basis-suffix typo pattern — see the architecture note above) — an invalid basis set or unsupported functional outside those two cases is still only caught when the engine itself fails at runtime, surfaced via `check_job_status`'s error text. `generate_job_input`/`submit_job` do automatically retrieve grounding excerpts from the manuals KB (see the architecture note above) and surface them to both the LLM and the human approver, but this is retrieval, not verification — nothing parses the retrieved text or blocks submission if a parameter looks wrong against it. A failed job also now triggers an automatic investigate-and-retry cycle (see the architecture note above) that often self-corrects exactly this kind of error, capped at `MAX_AUTO_RETRIES` (3) attempts per failure chain before the agent is instructed to stop and ask the user instead of retrying indefinitely.
- Dynamic tools (`create_tool`) run subprocess-isolated but are *not* sandboxed against a malicious or buggy human reviewer — `validate_tool_code`'s import/call restrictions and mandatory approval are a meaningful bar, not a guarantee; approved code has the same filesystem access as the rest of the app. There's also no tool-versioning: registering over an existing name (`overwrite=True`) replaces it outright, and any conversation with that tool already in its history will describe the old behavior if a user asks about it later.
- `web_search` is the only tool in this app that calls out to the public internet (everything else -- the LLM, embeddings, QC engines, KB -- runs locally); it sends the query text (which may include job parameters or error text) to DuckDuckGo. It's read-only and ungated like `search_knowledge_base` (no approval pause), on the reasoning that a search query carries the same risk profile as a search, not an action -- but it's a genuinely different trust boundary from the rest of the app worth knowing about if that's ever revisited. `web_search` wraps its call in a broad `except Exception` and returns an explanatory string rather than raising, since DuckDuckGo rate-limiting is routine, not exceptional.
- QM software this app doesn't wrap at all (Gaussian, NWChem, Q-Chem, Psi4, Molpro, ...) has no execution path whatsoever, by design -- `job_type='custom'` (see the architecture note above) is still ORCA/BAGEL-only, since `JobManager`'s worker dispatch (`_WORKER_MODULE`) only ever resolves `pyscf`/`orca`/`bagel`. Preparing an input for one of those is purely a prompt-guided behavior (`app/agent/prompts.py` tells the agent to compose the text directly in its chat reply, informed by `search_knowledge_base(doc_type='manual')` if the user uploaded a manual for it, and to say plainly that this app can't run it) rather than a structural code path -- there's no interrupt, no approval card, and nothing to gate, since `default_engine`'s `ALLOWED_ENGINES` check already hard-rejects any attempt to actually call `generate_job_input`/`submit_job` with an engine outside `{pyscf, orca, bagel}` as a backstop if the agent tries anyway. The knowledge base itself has no per-manual "which software" metadata field (only `doc_type` in `{"manual", "paper"}`) -- recognizing that an uploaded manual is for, say, Gaussian rather than ORCA relies entirely on the manual's filename/content being distinctive enough for semantic search to surface it, the same as any other KB lookup in this app.
