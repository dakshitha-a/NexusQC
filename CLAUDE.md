# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A conversational computational-chemistry agent (WebMO-style): a React single-page app talking to a FastAPI backend that wraps a LangGraph tool-calling agent, backed by a local LLM served via Ollama's OpenAI-compatible endpoint. It resolves molecules by name/SMILES, elicits missing job parameters instead of guessing them, runs quantum chemistry jobs as background subprocesses across PySCF/ORCA/BAGEL, and answers follow-up questions from a RAG knowledge base of uploaded manuals/papers. A prior Streamlit UI (`app/main.py`, `app/ui/`) was fully retired and deleted once the React frontend reached parity — comments/notes below that reference "the still-running Streamlit UI" or `app/main.py` as a live fallback describe that now-removed transitional state; treat them as historical context on *why* a given design choice exists, not as a description of code that's still there.

## Running it

Two processes: the FastAPI backend and the Vite dev server for the frontend.

```bash
# Terminal 1 -- backend (binds to localhost only; single-user, local-only app)
source /home/qcuser/apps/miniconda3/etc/profile.d/conda.sh && conda activate qc-agent
cd /data/qcuser/9.LLM_for_CASSCF && PYTHONPATH=$PWD python3 -m server.main

# Terminal 2 -- frontend (system Node is too old for Vite; use a dedicated env)
conda activate node20   # conda create -n node20 -c conda-forge nodejs=20
cd /data/qcuser/9.LLM_for_CASSCF/frontend && npm run dev
```

Open the URL Vite prints (default `http://localhost:5173`); its dev server proxies `/api/*` to the backend on port 8000, so no CORS setup is needed for local use.

The `qc-agent` conda env (Python 3.11) has everything in `requirements.txt` installed. There is no test suite; the way to validate a *backend* change is to invoke the relevant runner function directly, e.g.:

```bash
PYTHONPATH=$PWD python3 -c "
from app.chemistry.molecule import resolve_molecule
from app.chemistry.jobs.base import JobSpec, get_job_manager
m = resolve_molecule('water')
spec = JobSpec(method='single_point', engine='pyscf', molecule=m.to_dict(), params={'method':'hf','basis':'sto-3g'})
print(get_job_manager().submit(spec))
"
```
or drive the LangGraph agent directly with `app.agent.graph.invoke_turn({"messages": [...]}, config)` to test a full conversational turn without the UI, or curl the FastAPI routes directly (`server/routes/`) once `python3 -m server.main` is running.

For *frontend* changes, launch both dev servers headless and drive the app with Playwright (`chromium` browser only — `playwright install chromium`, no `--with-deps`, no sudo available) rather than trusting a code read — several real bugs here only showed up under real browser interaction, not code inspection: React 18 Strict Mode's dev-mode double-invoke of effects (mount→cleanup→remount) nulls a ref *before* running its cleanup function, so a "clear the container in cleanup" fix for a leaking 3Dmol WebGL context was silently a no-op; the actual fix clears the container at the *start* of the init effect instead (see `frontend/src/molecule/MoleculeViewer.tsx`). Also: `page.screenshot()`/`locator.screenshot()` cannot reliably capture WebGL canvas content — use `canvas.toDataURL()` via `page.evaluate()` instead when verifying anything rendered by the molecule/MO-cube viewers.

## Architecture

**Job execution is fully decoupled from the agent/UI.** `app/chemistry/jobs/base.py`'s `JobManager` submits a `JobSpec` and immediately returns a `job_id`; the actual work runs in a subprocess (`python -m app.chemistry.jobs.{pyscf,orca,bagel}_worker <spec.json>`) so a crash or long-running calculation can never block the FastAPI server process or the agent's tool-calling loop. Status/results are written to `data/jobs/<job_id>/{status,result}.json` via atomic temp-file-then-rename writes (`_atomic_write_text`) — plain `write_text` truncates before writing, which races with the frontend's polling reads (`server/routes/jobs.py`, lock-free — see its module docstring for why this must never go through `read_state()`/`_graph_lock`). The `app.chemistry.jobs.registry` module is the single source of truth for which engine handles which method (`DEFAULT_ENGINE`/`ALLOWED_ENGINES`) and which params are required per job type (`REQUIRED_PARAMS`) — the agent's `submit_job` tool consults this to decide what to ask the user for, rather than hardcoding elicitation logic per method.

**Each engine's runner + worker pair follows the same shape**: `{engine}_runner.py` has pure functions `run_<method>(molecule, params) -> {"summary": ..., "artifacts": ...}`, and `{engine}_worker.py` is the subprocess entrypoint that dispatches by method name and writes the `JobResult`. PySCF results come straight from PySCF's own Python objects. ORCA/BAGEL have no structured output, so `orca_runner.py`/`bagel_runner.py` regex-parse plain-text output — those patterns were derived from actual runs on this machine's ORCA 6.1.1 / BAGEL 1.2.2 installs, not from documentation alone, because exact stdout formatting isn't guaranteed across versions. `N_CORES` in `config.py` is deliberately computed by shelling out to `nproc`, not `os.cpu_count()`/`os.sched_getaffinity()` — both of the latter report the host's full CPU count in this container (255), ignoring the cgroup quota actually granted, which silently made ORCA request far more MPI ranks than exist.

**LangGraph state (`app/agent/state.py`) needs `NotRequired` + custom reducers, not just `Optional`.** `AgentState.molecule` and `.active_job_ids` are side-channel fields tools mutate via `Command(update=...)`, separate from the `messages` ReAct loop. Two non-obvious requirements: (1) they must be `NotRequired[...]`, not just `Optional[...]` — on a brand-new thread the keys are genuinely absent, and `ToolNode` validates injected `state` against a pydantic model derived from this TypedDict *before* any tool body runs, so plain `Optional` still fails validation on every tool call in a fresh conversation; (2) they need custom reducers (`_last_molecule`, `_append_job_ids`) because a single LLM turn can emit multiple tool calls in one batch (e.g. `set_molecule` + `submit_job`, or two `submit_job` calls) that all read the same pre-batch state — without a reducer, LangGraph's default channel either silently overwrites one write with another or hard-errors on multiple writes in one step. `generate_job_input` accepts an optional `molecule_identifier` so it can resolve the molecule itself when the user names one in the same message as the job request, instead of depending on a same-batch `set_molecule` call whose effect it can't see yet; `submit_job` deliberately does *not* accept it (see below).

**`submit_job` gates actual execution behind a real LangGraph `interrupt()`, not just prompt instructions.** After building the `JobSpec` and rendering its input preview (`app/chemistry/jobs/preview.py`, dispatching to each engine's `build_input_text`/`build_input_preview`), it calls `interrupt({...})`, which pauses the graph and raises `GraphInterrupt`; `graph.invoke()` returns with the state plus a `__interrupt__` key instead of completing, and the paused task's payload is also readable later via `graph.get_state(config).interrupts` (wrapped as `pending_approval()` in `graph.py` so a page reload while approval is pending still shows the card). The UI resumes with `resume_turn(Command(resume=...))`. This means the safety property — no job runs without a human clicking Approve — holds even if the LLM never asks for confirmation itself, since the pause is structural, not prompt-dependent. The one sharp edge: per LangGraph's docs, *"the graph resumes from the start of the node, re-executing all logic"* — everything in `submit_job` before the `interrupt()` call reruns on resume and is discarded, including a fresh `JobSpec` with a **new random `job_id`** (`JobSpec.job_id`'s `default_factory` reruns too). Two consequences drove the actual design: (1) `submit_job` never resolves `molecule_identifier` itself (unlike `generate_job_input`) — a network-backed name lookup redone on every resume could return a different molecule than the one the user actually approved, or raise on a transient failure and crash the approval click outright (verified empirically: an exception in the pre-interrupt code path during resume propagates straight out of `resume_turn`, it is *not* caught into a ToolMessage the way a normal tool exception is); the molecule must already be committed to state via an earlier/separate `set_molecule` call. (2) The interrupt payload includes `spec.to_dict()`, and the UI round-trips that *exact* dict back through `Command(resume={"approved": True, "spec": ...})` — the actually-submitted job uses `JobSpec(**decision["spec"])`, not a locally-rebuilt spec, so the job that runs is always bit-for-bit what was shown and approved, regardless of what the discarded re-execution produces. `generate_job_input` (preview-only, no `interrupt()`, no re-execution) has none of these constraints and freely resolves `molecule_identifier` inline.

**The approval card lets the user hand-edit ORCA/BAGEL input text before running it, but not PySCF's.** ORCA (`.inp`) and BAGEL (JSON) are genuine text formats the engine binary parses itself, so editing them changes nothing about the trust model — the binary was always going to interpret whatever text it's given. PySCF has no such file: its "preview" (`pyscf_runner.build_input_preview`) is a synthetic driver script standing in for direct API calls, so there's nothing for an edit to actually change at execution time; the approval card renders it as read-only `st.code` instead of `st.text_area` (`_EDITABLE_ENGINES = {"orca", "bagel"}` in `components.py`). When the user edits the text, `render_approval_panel` validates it (`app/chemistry/jobs/validate.py` — structural/keyword sanity checks, not a full grammar: balanced ORCA `%...end` blocks including single-line self-closing ones like `%pal nprocs 8 end`, a recognized geometry block, valid element symbols; JSON validity + required blocks for BAGEL) **before ever calling `resume_turn`** — a typo gets caught and displayed in place with no LLM round-trip, and the interrupt stays pending so the user can fix it and click "Run edited" again. `submit_job` re-validates server-side too (defense in depth, not the primary gate) before writing the text into `spec.params["_raw_input"]`; `orca_runner`/`bagel_runner`'s `run_*` functions check for `_raw_input` first and use it verbatim (byte-identical to what was shown, not re-serialized) instead of regenerating from structured params, falling back to the old codepath when it's absent so a direct `JobSpec` submission (e.g. the testing snippet above) still works unchanged. Because an edit can change what the engine actually prints (a different method keyword, a different BAGEL `nstate`), the job-type-specific output parser may not find what it expects after a real run — both runners wrap summary-building in a `_safe_parse` helper that turns that into a clear "ran fine but couldn't parse X, raw output at \<path\>" error rather than a bare traceback or (worse) silently wrong numbers; this is a deliberate "best-effort" choice over trying to re-derive parser expectations from the edited text.

**Atom numbering is 1-based everywhere a user or the LLM references an atom** — the labels drawn in the React molecule viewer (`frontend/src/molecule/MoleculeViewer.tsx`, via 3Dmol's `addLabel`), the Z-matrix panel (`app/chemistry/zmatrix.py`), `orbital_indices`, and `coordinate.atoms` for `pes_scan` all agree on this, so a number a user reads off the 3D view is directly usable in a scan spec. RDKit's `rdMolTransforms` (used internally by `_internal_coordinate_scan` in `pyscf_runner.py`) is 0-based, so that function subtracts 1 right at its boundary rather than leaking the RDKit convention outward. `zmatrix.py`'s Cartesian→Z-matrix conversion picks reference atoms by nearest-previously-placed distance (not real bonding) and is validated by an independent NeRF-based Cartesian reconstruction (round-tripped to <1e-14 Å pairwise-distance error on water/CO₂/benzene/acetylene in ad hoc testing) — colinear reference triples (unavoidable somewhere in any strictly linear molecule) report a `0.0` sentinel dihedral rather than raising, since the dihedral is genuinely undefined there.

**Excited-state methods (CIS, TD-HF/RPA, TDA-DFT, TDDFT, EOM-CCSD, state-averaged CASSCF, CASPT2) route through existing job_types rather than one-job-type-per-method.** `tddft`'s `qc_method` ('hf' vs 'dft') combined with `use_tda` covers CIS/TD-HF/TDA-DFT/TDDFT — `tdscf.TDA`/`TDDFT` are dispatchers that pick their concrete implementation from the reference wavefunction's type, and an HF reference has no XC kernel, so TDA-on-HF *is* CIS; ORCA's `%tddft` module does the same auto-selection based on whether the keyword line is a functional or plain `HF` (confirmed: energies and oscillator strengths from a real ORCA CIS run agree with PySCF's `tdscf.TDA(scf.RHF(...))` to 5 decimal places). `eom_ccsd` is its own job_type (always post-HF-CCSD, no method choice) added specifically because PySCF's `EOMEESinglet` has no oscillator-strength/transition-dipole support at all (confirmed by inspecting the class — no such method, unlike `tdscf`'s built-in `oscillator_strength()`), while ORCA's `orca_mdci` module computes them by default; `DEFAULT_ENGINE["eom_ccsd"] = "orca"` for that reason, with PySCF available (energies only, explicit `oscillator_strengths_note` in the summary) if explicitly requested. CASSCF has the same asymmetry — none of PySCF/BAGEL's CASSCF paths compute oscillator strengths in this app, but ORCA's `%casscf` block does when given `DoDipoleLength true`, so `casscf` gained `orca` as a *non-default* allowed engine, and `default_engine()` takes an optional `params` argument so a caller passing `want_oscillator_strengths=True` gets mechanically routed to ORCA regardless of engine default — deliberately *not* left to the LLM to infer from phrasing, since this codebase has already hit one incident (see the `NotRequired` note above) where prompt-dependent behavior was misdiagnosed for hours instead of being a mechanical, testable rule. CASPT2 stays BAGEL-only and energies-only (ORCA doesn't implement CASPT2 — it has NEVPT2 instead) since no engine available here computes CASPT2 transition dipoles either. All of the above ORCA output formats (EOM-CCSD's `EOM-CCSD RESULTS (RHS)` energy block plus its `SPECTRUM FOR LEFT-RIGHT TRANSITION MOMENTS` oscillator strengths — the balanced choice among the three transition-moment tables ORCA prints by default, since the CC Hamiltonian is non-Hermitian and right-only/left-only are each one-sided; and CASSCF's post-convergence `CAS-SCF STATES FOR BLOCK` table, bounded to exclude the near-identical pre-convergence `INITIAL CI STATE CHECK` block that has the same `ROOT N: E=...` line shape) were derived from real ORCA 6.1.1 runs on this machine, not the manual alone, following the same practice as the original single-point/frequency/TDDFT regexes.

**The agent can write and register its own tools at runtime (`create_tool` in `tools.py`, `app/agent/dynamic_tools.py`), gated by the same `interrupt()`-based human approval as `submit_job`, not by prompt instructions.** Every dynamic tool is constrained to one fixed shape — a single Python module defining exactly `def run(params: dict) -> dict:` — deliberately, so the rest of the system never needs to safely introspect or execute untrusted code just to build a calling schema: `_make_tool()` in `dynamic_tools.py` wraps every persisted tool in an identical `StructuredTool` (verified that `InjectedState`/`InjectedToolCallId`/`Command` returns work through `StructuredTool.from_function` exactly like the `@tool` decorator, via a direct test) whose body shells out to `dynamic_tool_worker.py`, a subprocess entrypoint in the same shape as the QC job workers — crash containment, not a security sandbox (documented as such in `dynamic_tools.py`'s module docstring); the actual safety gate is `validate_tool_code()`'s AST-based import allowlist/banned-call blocklist (`eval`/`exec`/`compile`/`__import__`/`globals`/`locals`, no `subprocess`/`socket`/`shutil`/network) plus the mandatory human review step. Tools persist to `data/dynamic_tools/<name>.{py,json}` (gitignored, like the rest of `data/`) and `load_dynamic_tools()` re-scans that directory on every call rather than caching, so a tool approved in one session is available in any other without a restart. Because the compiled graph's `ToolNode` is built once from a fixed tool list at `build_graph()` time, a newly-approved tool needs the graph rebuilt to become callable (`invalidate_graph_cache()` resets `_compiled_graph` to `None`; the next `get_graph()` call rebuilds it from `get_all_tools()`'s current contents against the *same* persistent sqlite connection via `_get_checkpointer()`, not a fresh one, so rebuilding doesn't leak a connection or lose checkpointed state — verified that a second `SqliteSaver` wrapping the same connection sees state written through the first). **`invalidate_graph_cache()` must never be called from inside a tool function.** This was a real deadlock, not a hypothetical: `ToolNode` runs tool calls on its own `ThreadPoolExecutor` worker thread (confirmed empirically), not the thread that called `.invoke()` — so a tool that acquires `_graph_lock` blocks forever, since the calling thread is holding that same lock for the entire `.invoke()` call while it waits for the worker thread to finish, and the worker thread is waiting to acquire the lock the calling thread already holds. Switching `_graph_lock` to an `RLock` does *not* fix this (reentrancy only helps a lock's *own* thread reacquire it; these are two different threads) — `create_tool` only ever persists the tool to disk; `server/routes/tools.py`'s tool-approval endpoint calls `invalidate_graph_cache()` itself, from the request-handling thread, strictly after `resume_turn()` has already returned and released the lock.

**The React frontend separates polling from expensive rendering.** Job status/list is polled via TanStack Query (`frontend/src/lib/queries.ts`, `useJobQuery`/jobs-list hooks) hitting `server/routes/jobs.py`'s lock-free disk reads (`read_spec`/`read_status`/`read_result` — never `read_state()`/`_graph_lock`, so a polling tab is never stalled behind an in-flight chat turn anywhere in the process; see that module's docstring). The MO-cube viewer (`frontend/src/jobs/MoCubeViewer.tsx`) and other job-artifact viewers are mounted only when `JobDetailDrawer.tsx` opens for that specific job — React's own mount/unmount lifecycle achieves what a Streamlit `st.fragment` split had to do by hand: they're never rebuilt by an unrelated re-render or polling tick, so an in-progress WebGL rotation/zoom is never discarded from under the user. The live "tail -f"-style job log (`frontend/src/jobs/LiveLogPanel.tsx`, `GET /api/jobs/{id}/log`) *is* deliberately on its own 1.5s TanStack Query `refetchInterval` gated on `status === "running"` — a raw log tail is cheap, low-stakes state, not worth a second SSE event type.

**A chat turn from the composer is submitted via `POST /api/threads/{id}/messages`, which returns `202` immediately and runs the turn on its own background thread** (`_run_turn` in `server/routes/chat.py`), streaming progress to the browser over `GET /api/threads/{id}/events` (SSE, `server/sse.py`'s `SSEHub`/`event_stream`) rather than blocking the HTTP response — the same reason `stream_turn`/`stream_mode` exists over a blocking `invoke()` at all, just pushed one level further from a blocking Streamlit script to a blocking HTTP request. `_run_turn` requests `stream_mode=["updates", "messages"]` (`stream_turn_tokens` in `graph.py`) so real per-token text deltas (`"messages"` mode, confirmed empirically to arrive as genuine incremental chunks through Ollama's OpenAI-compatible endpoint, not one buffered blob) and tool-call progress (`"updates"` mode) come out of the same stream, published as `token`/`agent_step`/`message`/`interrupt`/`turn_complete`/`error` SSE events. The frontend renders the user's own message immediately (`optimisticUserMessage` in `frontend/src/lib/chatStore.ts`, before the POST even completes) and appends `token` deltas to an in-progress assistant bubble by `message_id`, then reconciles with the authoritative final `AIMessage` once the `message` event for it arrives — the same "don't wait for the whole turn to draw anything" fix the old Streamlit UI needed, achieved through real streaming instead of an `st.status` container. `_run_turn` holds `_graph_lock` for its entire iteration, same as `invoke_turn`/the old `stream_turn` — not a new contention source. `resume_turn` (job/tool approval, `POST /api/threads/{id}/approvals/{job,tool}`) is deliberately left non-streaming (a single blocking call): those are one-click resumes with no user-authored message to render early, so `_publish_new_messages` in `chat.py` just diffs message ids before/after the call and publishes whatever's new once it returns.

**The UV/Vis plot tool (`plot_excited_state_spectrum` in `tools.py`) writes its PNG as a job artifact after the job already completed**, not as part of the original `JobResult` — it reads the completed job's `summary` (`excitation_energies_eV`/`oscillator_strengths`), Gaussian-broadens them (`app/chemistry/spectrum.py`, headless `matplotlib.use("Agg")`), saves the image into that job's `data/jobs/<id>/` directory, then re-reads and re-writes `result.json` via `read_result`/`write_result` with an added `artifacts["uvvis_spectrum"]` path. It refuses outright (no plot, no job dirs touched) rather than rendering a flat/fabricated line when `oscillator_strengths` is missing, `None`, or all-zero — the exact situation for a PySCF `eom_ccsd`/`casscf` job or any `caspt2` job, per the paragraph above. `frontend/src/jobs/UvVisPanel.tsx` just displays whatever artifact path is on disk, mounted inside `JobDetailDrawer.tsx` like the MO-cube viewer for the same "don't rebuild on a polling tick" reason.

**The React molecule viewer (`frontend/src/molecule/MoleculeViewer.tsx`, `frontend/src/jobs/MoCubeViewer.tsx`) is a hand-rolled imperative wrapper around the `3dmol` npm package**, not a normal declarative component — the 3Dmol viewer instance and its model state live in a `useRef`, rebuilt only via an effect keyed on the molecule/cube data itself, because putting `$3Dmol.createViewer(...)` calls directly in the render path would rebuild the WebGL view (and discard camera rotation/zoom) on every unrelated re-render. It is read-only (numbered atom labels only, no click-to-select bond/angle/dihedral measurement) — an earlier version had that feature, ported from a prior Streamlit custom component, but it was dropped after surfacing more trouble than it was worth (see git history around the React rewrite for what that entailed). One non-obvious bug shaped the current implementation, confirmed by direct browser testing rather than reasoning from the 3Dmol/React docs alone: **`GLViewer` has no `destroy()`/`dispose()`/`remove()` method, and `createViewer()` unconditionally appends a new `<canvas>` (its own WebGL context) into the given container.** React 18 Strict Mode's dev-mode double-invoke of effects (mount→cleanup→remount) nulls the container ref *before* running the effect's cleanup function, even though the actual DOM container node is *not* torn down across that synthetic cycle — so a cleanup-only "clear the container" fix is silently a no-op, and the first mount's orphaned `<canvas>` is still sitting in the container when the second mount's `createViewer()` appends another one on top of it. Browsers cap the number of live WebGL contexts per page (commonly 8–16); repeated mount/unmount without fixing this (e.g. switching between conversations, collapsing/reopening a panel) exhausts that cap, and every new context after that silently fails to initialize — the viewer renders as a blank square with no error, which was a real user-reported bug. The actual fix: clear the container (`containerRef.current.innerHTML = ""`) unconditionally at the *start* of the init effect, before creating a new viewer, not just in the cleanup function — verified via debug instrumentation that live canvas count stays at exactly 1 across dozens of rapid mount/unmount cycles after this change, was 2+ (and growing) before it.

**`generate_job_input`/`submit_job` mechanically query the manuals/reference-docs KB on every call, not just when the LLM decides to.** `search_knowledge_base` (`app/rag/query_tool.py`) is a normal LLM-discretionary tool with only a soft system-prompt instruction to use it for exact syntax — nothing forced the agent to actually call it before generating input, and in practice it didn't: a real job (DFT geometry optimization on uracil) was submitted with the PySCF basis string `"6-31gd"`, which PySCF doesn't recognize (its Pople-basis parser only accepts `*`/`**` suffixes or a parenthesized `(d)`, e.g. `"6-31g(d)"`/`"6-31g*"` — `"6-31gd"` isn't a registered alias), and the job failed at runtime with an unhelpful raw `KeyError` traceback instead of being caught earlier. Since this codebase already treats "left to the LLM's discretion" as an unreliable mechanism for anything safety- or correctness-critical (see the CASSCF oscillator-strength routing note above), the fix was to make the KB lookup structural: `_build_spec_or_error` in `tools.py` (the function shared by both tools) now always calls `_kb_context_for_job()`, which runs a `similarity_search` filtered to `doc_type="manual"` using the engine/job_type/method/functional/basis as the query, and returns whatever it finds (or `""` on an empty/unreachable store — best-effort, not a hard gate). The result is threaded through both call sites: `generate_job_input` appends it to the ToolMessage the LLM sees (with an instruction to cross-check parameters against it), and `submit_job` adds it to the `interrupt()` payload so `frontend/src/approvals/JobApprovalCard.tsx` shows it under a "Manual/reference excerpts consulted" section on the human approval card — the last checkpoint before a job actually runs, and the one place this doesn't depend on the LLM reading anything at all. This is retrieval-and-surface, not verification: nothing parses the retrieved text or blocks a bad parameter automatically, and the underlying KB content quality varies by engine (ORCA/BAGEL's crawled manuals document keyword syntax directly; PySCF's KB is generated from installed-package docstrings, which cover class/method signatures well but don't document basis-set naming conventions at all, so KB grounding is weaker for exactly the class of error that motivated this — confirmed by testing `_kb_context_for_job` against real queries). This manual-only filter is deliberately *not* extended to `doc_type="paper"` or to the academic-literature tool described below — this lookup exists purely for software syntax/keyword grounding, and papers would add surface to the approval card with no correctness gain for that specific check. Conceptual/molecular-background questions are a separate, prompt-guided knowledge-source category (see `app/agent/prompts.py`'s `SYSTEM_PROMPT` and the paragraph below on `search_academic_literature`).

**Config is centralized in `app/config.py`**, all overridable via `QC_AGENT_*` env vars: `LLM_MODEL` (default `qwen3:30b`), `LLM_BASE_URL`/`EMBEDDING_MODEL` (Ollama), `ORCA_BIN`/`BAGEL_BIN`/`BAGEL_ONEAPI_SETVARS`, `N_CORES`, `MAX_CONCURRENT_JOBS`. The LLM client in `app/agent/graph.py` sets `timeout=150, max_retries=0, max_tokens=1024` — defensive bounds for a locally-hosted model, not a fix for any specific known bug (an earlier multi-minute stall was misdiagnosed as model "thinking" behavior; the real cause was the missing `NotRequired` above, which made every tool call fail and loop).

## Knowledge base seeding

`scripts/seed_knowledge_base.py` crawls the BAGEL and ORCA manuals and generates PySCF reference docs from the *installed* `pyscf` package's docstrings (194 sources, ~4000 chunks total). PySCF is deliberately not scraped from pyscf.org — its `robots.txt` explicitly disallows `ClaudeBot` (`Content-Signal: ai-train=no`) — so `extract_pyscf_docs()` walks `inspect.getdoc()` over the key classes instead. Watch for dispatcher functions there: `mcscf.CASSCF`, `mp.MP2`, and `tdscf.TDA` at the top level are runtime dispatchers with *no docstring of their own* (0 chars) — the real content lives on the concrete classes they resolve to (`mcscf.mc1step.CASSCF`, `mp.mp2.MP2`, `tdscf.rhf.TDA`), so always extract from those, not the dispatcher. The crawler also force-corrects encoding via `apparent_encoding` when a server omits `charset` in `Content-Type` — `requests` otherwise silently falls back to ISO-8859-1 and mangles curly quotes/em-dashes (hit this on the ORCA manual).

## Automatic failed-job troubleshooting and retry

**A failed job triggers an automatic investigate-and-retry cycle, but the retry budget is enforced by code, not by the LLM counting its own attempts.** `app/agent/job_watcher.py` — a background thread started once at server startup, walking every conversation in the registry rather than being tied to any particular browser tab or request (see its module docstring for why: a closed tab must not silently stop auto-retry, and two open tabs on the same conversation must not both inject the same retry) — branches on status: a failed job gets a system notice instructing the agent to call `check_job_status`, then `search_knowledge_base(doc_type="manual")` and (if that's insufficient) the `web_search` tool (`app/agent/web_search.py`, DuckDuckGo via the `ddgs` package) — deliberately not `search_academic_literature`, since that tool covers published papers, not software error messages or syntax (see the knowledge-hierarchy paragraph below) — then call `submit_job` again with corrected parameters and `retry_of_job_id` set to the failed job's id — which still pauses on `interrupt()` for human approval exactly like any other `submit_job` call, so "the agent silently reruns a job with different parameters" is never possible; the human always sees the diff before it runs (the approval card shows a "🔁 Retry attempt N of M" banner and the corrected parameters). The budget cap (`MAX_AUTO_RETRIES = 3` in `app/chemistry/jobs/base.py`) is *not* read from anything the LLM supplies: `count_failed_in_chain()` walks a retry chain backward on disk via each job's `params["_retried_from"]` (written by `submit_job` itself when `retry_of_job_id` is passed) and counts how many jobs in it currently have `status == "failed"`, and `job_watcher.py` calls this directly before deciding which notice to send — an "auto-retry" notice below the cap, or a "stop and explain, do not retry" notice at/above it. This split exists because an LLM-tracked counter keyed on an optional argument it might simply omit resets to zero for free, which is exactly the "prompt-dependent behavior" this codebase has already been burned by once (see the `NotRequired` note above) — `submit_job`'s own `_retry_count` bookkeeping is provenance for the approval card's display only, never the gate. `read_spec()` (the same file's `read_status`/`read_result` pattern) returns `None` rather than raising on a missing/corrupt `spec.json`, since it's called from `submit_job`'s pre-`interrupt()` code path, which re-executes in full on every resume — an exception there kills the approval click outright rather than being caught into a `ToolMessage` (see the `submit_job` architecture note above). `check_job_status` also now includes the failed job's original `job_type`/`engine`/params in its report (previously just the raw traceback) — confirmed via direct testing to matter in practice: without it, the model correctly identified the right basis-set fix from the KB context but then guessed the wrong `job_type` for the retry (since nothing told it what the original job actually was) and never got as far as a corrected approval card.

**Knowledge access is task-dependent, not one undifferentiated pool.** The agent has four sources — the mechanical manuals-only KB lookup above (input prep), `search_knowledge_base` (LLM-discretionary, filterable by `doc_type` — `"manual"` or `"paper"`), `search_academic_literature` (`app/agent/scholar_search.py`, wraps the Semantic Scholar Graph API), and `web_search` — and `app/agent/prompts.py`'s `SYSTEM_PROMPT` gives each a distinct ordered hierarchy keyed to a recognizable situation (preparing a job input, troubleshooting a failed job, answering a general chemistry/method/active-space question, or writing a new tool/parser) rather than one flat "use this when relevant" instruction, since the four situations call for genuinely different sources and mixing them risks e.g. surfacing a software manual snippet for a chemistry-judgment question. `search_academic_literature` stands in for "Google Scholar," which has no official/free API and would otherwise require unreliable scraping (e.g. the `scholarly` package, prone to CAPTCHA blocks): it hits Semantic Scholar's `/graph/v1/paper/search/bulk` endpoint specifically, not `/paper/search` — confirmed empirically that the latter (relevance-ranked, no `sort` param) returns `429 Too Many Requests` repeatedly on the shared unauthenticated pool, while `bulk` both fared better and is the only endpoint supporting `sort=citationCount:desc` (the tool's `mode="seminal"`) or `sort=publicationDate:desc` (`mode="latest"`). Reliable day-to-day use likely needs a free API key (`QC_AGENT_SEMANTIC_SCHOLAR_API_KEY`) — the tool degrades gracefully without one (a `429` response returns an explanatory string telling the agent to fall back to `web_search` rather than retrying), so this isn't a hard blocker, just an expected-in-practice condition. Bulk's query syntax is literal boolean AND/OR of bare/quoted tokens, not semantic search, which is a real usability trap confirmed by direct testing: a natural multi-word question (e.g. "what active space should I use for CASSCF calculations of retinal photoisomerization excited states") returns zero hits since every bare word is ANDed together, while unquoted common words (`active space`) match hundreds of irrelevant papers by loose word overlap — only a query built from a few double-quoted, distinctive multi-word technical terms (`"active space" "CASSCF" "retinal"`) returns a clean, relevant result set. This is enforced entirely via the tool's own docstring contract (with explicit good/bad examples), the same way `doc_type` selection on `search_knowledge_base` is already prompt-guided rather than code-mediated — there is no query-rewriting layer.

## Known limitations

- `pes_scan`'s two-endpoint mode (`_liic_cartesian` in `pyscf_runner.py`) does Cartesian interpolation between structures, not true internal-coordinate LIIC. The single-coordinate scan mode (bond/angle/dihedral via `_internal_coordinate_scan`) is proper internal-coordinate manipulation via RDKit's `rdMolTransforms`.
- `/data` is at ~96% full; the KB uploader and MO cube files have no size/retention cap.
- BAGEL's standalone `casscf` job type and `pes_scan` driven through the chat agent (rather than called directly) are less thoroughly tested than the other paths.
- Hand-editing the approval-card input is only available for ORCA and BAGEL, not PySCF (no literal input file to edit — see the architecture note above). Edited-input validation is structural/keyword sanity checking, not a real dry-run (neither engine offers one); a syntactically valid edit can still fail chemically or fail to parse afterward.
- Oscillator strengths for CASSCF (via `want_oscillator_strengths=True`) and EOM-CCSD are only ever available via ORCA in this app — PySCF and BAGEL report excitation energies only for these methods, and CASPT2 (BAGEL-only, since ORCA has no CASPT2) is energies-only with no engine-of-choice workaround. `plot_excited_state_spectrum` refuses cleanly in these cases rather than plotting a flat/fabricated spectrum.
- No pre-flight basis-set/keyword *validator* exists for ORCA/BAGEL/PySCF beyond the approval-card's structural sanity checks (`validate.py`) — an invalid basis set or unsupported functional is still only caught when the engine itself fails at runtime, surfaced via `check_job_status`'s error text. `generate_job_input`/`submit_job` do automatically retrieve grounding excerpts from the manuals KB (see the architecture note above) and surface them to both the LLM and the human approver, but this is retrieval, not verification — nothing parses the retrieved text or blocks submission if a parameter looks wrong against it. A failed job also now triggers an automatic investigate-and-retry cycle (see the architecture note above) that often self-corrects exactly this kind of error, capped at `MAX_AUTO_RETRIES` (3) attempts per failure chain before the agent is instructed to stop and ask the user instead of retrying indefinitely.
- Dynamic tools (`create_tool`) run subprocess-isolated but are *not* sandboxed against a malicious or buggy human reviewer — `validate_tool_code`'s import/call restrictions and mandatory approval are a meaningful bar, not a guarantee; approved code has the same filesystem access as the rest of the app. There's also no tool-versioning: registering over an existing name (`overwrite=True`) replaces it outright, and any conversation with that tool already in its history will describe the old behavior if a user asks about it later.
- `web_search` is the only tool in this app that calls out to the public internet (everything else -- the LLM, embeddings, QC engines, KB -- runs locally); it sends the query text (which may include job parameters or error text) to DuckDuckGo. It's read-only and ungated like `search_knowledge_base` (no approval pause), on the reasoning that a search query carries the same risk profile as a search, not an action -- but it's a genuinely different trust boundary from the rest of the app worth knowing about if that's ever revisited. `web_search` wraps its call in a broad `except Exception` and returns an explanatory string rather than raising, since DuckDuckGo rate-limiting is routine, not exceptional.
