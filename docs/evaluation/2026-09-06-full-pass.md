# Test and evaluation pass, 2026-09-06

A record of what was run, what it covers, how to reproduce it, and what each
result means. Written to the standing rule for this repository: **no evaluation
figure appears without saying what the test was, what its denominator counts,
what counts as a pass, and what the result means.** A number nobody can
reconstruct from the prose is worth less than no number at all.

The pass ran alongside the CAS engine closeout, so results are stamped with the
commit that produced them.

## What exists to be run

Four bodies of tests and evaluations, with different requirements. Knowing which
is which is not bookkeeping: most of what looks like failure in a first run is a
suite being asked to do something this environment cannot give it.

| Suite | What it is | Scripts | Needs |
|---|---|---|---|
| `tests/backend/` | standalone invoke-and-print scripts | 141 | 103 run in process; 38 need a live stack or `docker compose` |
| `tests/frontend/` | raw Playwright specs, chromium, no test runner | 37 | the stack, and a built `frontend/dist` |
| `tests/e2e/` | agent-driven end-to-end scenarios plus UI specs | 22 + 11 | the stack, a live model, engine licences |
| `scripts/casbench/` | the CAS benchmark's six evaluation sets | 6 sets | in process, no stack, hours of CPU |

Plus five standalone validators under `scripts/`, which are gating numerical
checks rather than suites.

**The backend suite cannot be run from a git worktree.** Thirty-eight of its
scripts either drive the stack over HTTP or shell out to `docker compose exec`,
and `COMPOSE_DIR` is the repository root, so from a worktree that resolves to a
compose project with no containers. This is why the full backend pass runs from
the main checkout and the in-process subset runs anywhere.

## The in-process backend subset

**What it is.** The 103 of 141 backend scripts that need neither a live stack
nor `docker compose`. They exercise the chemistry core, the agent graph, the
job registry and the taxonomy, all in process against the code as imported.

**How to reproduce.**

```bash
export PYTHONPATH=$PWD QC_AGENT_LLM_BASE_URL=http://localhost:11434/v1
python3 tests/backend/<script>.py     # each is standalone, exit 0 is a pass
```

**Result: 85 of 103 exit clean.** The 18 that do not are grouped by cause
below, because the grouping is the finding: none of them is a defect in the
code under test.

| Cause | Scripts | What it means |
|---|---|---|
| needs the auth bootstrap | 13 | they refuse to start without `QC_AGENT_TEST_ADMIN_PASS`, which `_00_bootstrap.py` prints, and that script needs the compose stack |
| engine binary missing | 4 | `FileNotFoundError: '/opt/orca/orca'`, the generic default in `app/config.py`. This host installs licensed engines under `/software` and the real paths live in the project-root `.env`, which a fresh worktree does not have |
| a job failed to reach `completed` | 1 | `p7_03`, 19 of 22 checks passing, the three failures all being a job that did not finish; same missing-engine cause |

So the honest reading of "85 of 103" is that **every script whose requirements
this environment actually met passed**, and the remainder were asking for a
stack or an engine that was not there. Copying `.env` into the worktree resolves
the engine group; the auth group is deferred to the full run from the main
checkout.

## The standalone validators

These are gating numerical checks, run after touching the code they guard
rather than on a schedule.

**`validate_orbital_character`** checks `classify_orbital_character` against
orbitals whose sigma/pi/n assignment is not in doubt, water and ethylene being
the anchors it was built from, and additionally that the diffuse-basis note is
attached by the worker rather than invented by the job. **All checks pass**,
including that a nitrogen lone pair is localised on the nitrogen alone and that
a table lacking the diffuseness column gets no note.

**`validate_wigner_sampling`** is the gating check for the Wigner sampler, and
it verifies three independent things rather than one. That
`reduced_masses_from_normal_modes` reproduces PySCF's own `reduced_mass`:
**worst relative deviation 6.18e-16 over 3 modes and 8.11e-16 over 6**, which is
floating-point agreement. That the sampled ensemble's true Cartesian mean
potential energy matches the analytic harmonic value: **1.13% and 1.11% against
a 3% tolerance**, where a deficit tracking the square root of the reduced mass
would mean the width was being applied to a non-unit mode vector. And that the
ensemble has no centre-of-mass drift once translational modes are excluded:
**0.000000 Angstrom**. **All checks pass.**

The remaining three validators need engines or long runs and are covered by the
full pass.

## The full backend suite, against the live stack

**What it is.** All 139 scripts in the default set, run from the main checkout
against the compose stack, which is where they have to run: 38 of them drive the
API over HTTP or shell out to `docker compose exec`.

**How to reproduce.**

```bash
QC_AGENT_TEST_BASE_URL=https://127.0.0.1:8444 bash tests/run_backend.sh
```

**Result: 138 of 139 scripts report all checks passing.** The one that does not
is `batch_01_multi_geometry.py`, comparing an artifact path the batch
orchestrator recorded against the host filesystem. A batch's artifacts mix host
paths, written in process, with `/app/data` paths written by the orchestrator
inside the container; the two name the same bytes through the
`./data:/app/data` bind mount and only one exists from where the script runs.
Fixed after this run, so a re-run would be 139 of 139.

**This run also destroyed the job stack**, taking it from 275 jobs to 1, and
that is a finding rather than an aside. See "The purge nobody had quarantined"
below.

## The end-to-end scenarios

**What it is.** `tests/e2e/` drives the whole product as an ordinary user
account through real agent turns against a live model: a natural-language
request, an approval card whose parameters are asserted, an approval, a job
polled to a terminal state, its summary checked for what that job type should
produce, and every declared artifact downloaded.

**Preflight: 16 of 16.** Worth listing because it is what makes the rest
meaningful: `/api/health` through nginx, `N_CORES` resolving to 4 rather than
the container's 255, `mpirun` present and OpenMPI 4.x rather than 5.x (which
dropped the C++ bindings BAGEL links against), BAGEL's libraries all resolving
under their scoped path, the ORCA binary executable, the licensed trees mounted
read-only, nginx forwarding `Host $http_host` so the same-origin CSRF fallback
works, and nginx serving the frontend bundle that is on disk rather than one
baked into an image.

**Job matrix, tier 1: 69 of 73 checks.** Before this pass it was 56 of 73, and
twelve of those seventeen failures were one stale assertion demanding the agent
call `submit_draft` on a path where the system prompt tells it not to. The four
that remain are M10, M13 and M26 failing to reach an approval card at all, which
is agent behaviour rather than a stale expectation and is left standing.

## Latency and concurrency, on a card this app has to itself

**What it is.** `perf_02_ttft_and_concurrency.py` measures warm time to first
token and what happens when four people use the deployment at once. It carries
its own history: the standing "6 to 32 s, median about 15 s" was an n=4 sample
from 2026-08-16 that predates the keep-warm loop, and it is quoted in
user-facing text.

**Why it could not be settled before.** The interesting number is not the
absolute latency but the split: how much of the slowdown under load is this
app's doing and how much is the model server's. That ratio needs a baseline
measured against a card nothing else is using. Sampled twice in one run on a
shared card it came back 3.05x and 0.95x, so the script reported the split as
unavailable rather than assert one. GPU 0 on this host is reserved for NexusQC
and Ollama serves only NexusQC, which is what made this measurable; no code
changed.

**Result.**

| measurement | value |
|---|---|
| warm TTFT, n=12 | median **2.49 s**, range 1.44 to 3.81 s |
| four at once, pooled over 3 bursts, n=12 | TTFT median **6.47 s**, whole turn 8.32 s |
| stack slowdown under that load | 2.60x |
| the model server's own share of it | 2.13x |
| **what the app adds on top** | **1.22x** |

So the app multiplies the model server's own concurrency penalty by about a
fifth, which is small, and the honest reading of "about 6.5 s to a first token
with four people at once" is that most of it is the server reserving a KV cache
per slot rather than anything this code does. Four concurrent turns still
finish faster than four serial ones, 14.8 s against about 17 s, so the
concurrency is real work rather than queueing.

The old "6 to 32 s, median about 15 s" figure is superseded: warm, on the
current deployment, it is 2.49 s at the median.

## The purge nobody had quarantined

The backend run above took the stack from 275 jobs to 1, and the mechanism is
worth writing down because the same thing happened on 2026-08-28 and the fix
made then was incomplete.

`run_backend.sh` excluded `p1_07_purge_status_source.py` because it calls
`POST /api/admin/purge/jobs`, which is `purge_all_jobs` and destroys everything
on the stack rather than only what the suite created. That exclusion was written
from memory of which script it was rather than from what scripts call:

```bash
grep -l "admin/purge/jobs" tests/backend/*.py
```

returns four. `conf_01_require_admin_boundary.py` is safe, asserting only that a
non-admin gets 403. `p1_03_admin_config_purge_audit.py` and
`perf_02_admin_storage_latency.py` are not: both call it as admin, and both
appear in the run log reporting `purge/jobs succeeds -- 200` with the audit
entry recording `purge_all_jobs`.

The check that should have caught it could not. `zz_99_job_cleanup.py` computed
`leftover = list_job_ids(admin) - baseline`, a one-sided difference that finds
what a run added and is structurally blind to what it destroyed. Its own output
on this run says "39 job(s) pre-existed, 10 present now" and then reports PASS.

All three purging scripts are excluded now, the runner's header records the grep
so the list gets derived rather than remembered, and both cleanup scripts assert
the other direction as well.

## The CAS benchmark

Six evaluation sets, described in full in
[`../CAS_ENGINE_METHOD.md`](../CAS_ENGINE_METHOD.md) §3, whose per-molecule
ledgers are committed under [`../casbench/`](../casbench/). Reproduce with
`python3 -u scripts/casbench/run_bench.py --set all`.

Results from the closing sweep are recorded in the ledgers themselves, each
stamped with the commit whose engine code produced it, and interpreted in the
method document rather than here. What belongs here is the reproduction and the
scope: the sets run in process, need no stack, and take roughly five and a half
hours end to end on this host at `omp=8, mkl=12`.

## Suite drift found by this pass

The pass was asked to bring the suites up to date, and the drift it found is
listed here because a suite that has drifted is a suite reporting on code that
no longer exists.

| What | Where | Consequence |
|---|---|---|
| subtype `autocas` in the only `cas_reco` end-to-end cell | `tests/e2e/_probes.py` | the CAS engine had no working end-to-end coverage. `reg2b_03_matrix_v2_taxonomy.py` would have caught it and had not been run since the 2026-09-02 rebuild |
| `target_state` passed to `single_point/grad` | `tests/e2e/_probes.py` M28 | that parameter belongs to opt, freq, opt_freq and neb_ts; grad takes `target_states`, a list |
| a `pes_1d` master asserted to hold no keys | `tests/e2e/e2e_08_job_matrix.py` | a real completed master carries five, two of them written unconditionally |
| three registry pairs with no cell | `tests/e2e/_probes.py` | `pes_1d/ee`, `interp_pes` and `interp_pes/ee` were reachable by an ordinary request and untested end to end |
| a guarded-parameter count frozen at 15 | `tests/backend/agent_09_unstated_parameters.py` | a sixteenth was guarded, so the script failed with a detail naming nothing |
| fixtures built on `cas_reco/autocas` and `/avas` | `tests/backend/p8_02_cas_reco_followup.py` | passed anyway, because the classification reads the task and never the subtype |

Each is fixed, with the fix and its evidence recorded in `docs/TRACKER.md`.
